ORA Command Center Mirror — Drift & Health Check (CC/MCP fleet)

PURPOSE: this is the alerting layer for the native Windows Scheduled Task "ORA Command Center - Mirror Deploy" (registered via C:\Users\Owner\oxford-command-center\scripts\register-mirror-task.ps1; runs scripts\deploy-mirror.ps1 hourly all day + a guaranteed 06:45 ET trigger). That script was patched 2026-07-09 via PR #192 ("fix(deploy): mirror deploy fast-forwards to origin/main before baking") to `git fetch origin` + `git pull --ff-only` before baking, and now `throw`s/aborts the deploy on a diverged-or-dirty tree instead of silently redeploying stale code (the original incident: local main sat 7 commits behind origin for an unknown period while the hourly job kept redeploying pre-retokenization code with only a fresh data snapshot — "baked Nm ago" reflects data freshness, not code freshness). PR #192 fixed the silent-stale-deploy failure mode, but added no alerting of its own, and the task itself lives entirely OUTSIDE this MCP scheduled-task registry (registered via native `Register-ScheduledTask`, not `create_scheduled_task`) — so it is invisible to any dead-man-heartbeat logic that only walks `list_scheduled_tasks`. If the pull ever throws (genuine divergence or a conflicting dirty tree), the mirror would otherwise just silently stop advancing with nobody notified. Full incident history and root-cause detail: memory file `reference_command_center_mirror_deploy_gap.md` in `~/.claude/projects/C--Users-Owner-OneDrive---Oxford-Capital-Partners/memory/` — read it if anything below is ambiguous.

KNOWN LIMITATION (do not silently paper over this in the Notion row): this CC/MCP scheduled task only fires while Claude Desktop is open — it is a business-hours-ish sampling check layered on top of the native task, NOT a 24/7 replacement for it. If Desktop was closed all day, this check simply didn't run that day; that is expected behavior of this fleet, not a defect to report.

STEPS:

1. `cd "C:/Users/Owner/oxford-command-center"` then `git fetch origin --quiet` (READ-ONLY — do not pull, merge, stash, or otherwise modify the tree). Paths in this file are deliberately forward-slashed AND quoted: in the Bash tool an unquoted backslash is an escape character, so a bare `C:\Users\...` silently collapses to `C:UsersOwner...` and the command dies before it runs. Do not "tidy" them back to bare backslashes.
2. Drift count, BOTH directions — behind and ahead are different hazards and you need both:
   - Behind: `git rev-list --count HEAD..origin/main`. A nonzero value alone is NOT an alarm (see step 5).
   - **Ahead: `git rev-list --count origin/main..HEAD`.** Nonzero here is a FLAG. It means the mirror is deploying commits that exist on no remote — unreviewable on GitHub, and destroyed if local main is ever reset. Found live on 2026-08-03: commit `3692385` (a lease-snapshot auto-refresh) had sat ahead, unpushed, for five days while this check reported "drift 0 = clean," because v1.0/v1.1 measured only the behind direction. If ahead > 0, name the commits (`git log origin/main..HEAD --oneline`) in the Notion row and recommend a push/PR; do NOT push them yourself.
3. Working-tree state: `git status --short`. Classify each entry by RUNNING THE TEST below, not against a remembered file list. (A hardcoded baseline list was tried first and rotted within two weeks — by 2026-07-24 it was stale in BOTH directions: none of its four entries were present anymore, while an unlisted-but-harmless untracked plan doc was. The question that matters is never "is this file on a list" but "can this entry abort `git pull --ff-only`".)
   - **Untracked (`??`) with no counterpart on `origin/main` → BENIGN.** Verify: `git ls-tree origin/main -- <path>` returns empty. Nothing incoming can be overwritten, so the pull cannot abort on it. Recurring instances: plan docs under `docs/superpowers/plans/`, `.wrangler/`, `scripts/dev-watchdog.cjs`.
   - **Untracked (`??`) that DOES exist on `origin/main` → FLAG.** This is the untracked case that genuinely aborts `pull --ff-only` ("untracked working tree file would be overwritten").
   - **Modified (` M`) but EOL/whitespace-only → BENIGN.** Verify: `git diff --ignore-all-space --ignore-cr-at-eol -- <path>` returns empty. This is the recurring *Command Center CRLF Hazard* (`reference_command_center_crlf_hazard.md`). `.claude/launch.json.example` and `package.json` have historically shown up here as local-dev deltas — that history is context, NOT an exemption: run the test on them like anything else and FLAG if the diff is substantive.
   - **Modified (` M`) with substantive content, OR any staged/conflicted status (`UU` `AA` `DU` `AU` `DD` `M ` `A ` `D `) → FLAG.**
   - **Any REBASE/MERGE-in-progress marker → FLAG.** Check `.git/MERGE_HEAD`, `.git/REBASE_HEAD`, `.git/CHERRY_PICK_HEAD`, `.git/rebase-merge/`, `.git/rebase-apply/` — any of these indicates a stuck `git pull --ff-only` failure from deploy-mirror.ps1.
   Corroborating evidence, never a substitute for the tests above: if the native task's `LastTaskResult` is 0 and `LastRunTime` post-dates the entry's mtime, the deploy has already run successfully WITH that entry present. Record every entry you classified BENIGN in the Notion row along with the verification command output — benign is a conclusion you show your work for, never a silent skip.
4. Native task health + run classification — **run the classifier, do not hand-reason this**:
   ```
   powershell -NoProfile -ExecutionPolicy Bypass -File "C:/Users/Owner/oxford-command-center/scripts/mirror-run-classify.ps1"
   ```
   It emits one JSON object and is strictly read-only (it does NOT fetch — step 1 already did). Fields: `lastRunTime`, `lastTaskResult`, `nextRunTime`, `runEndedAt`, `beaconPresent`/`beaconStatus`/`beaconOutcome`, `gitBehind`/`gitAhead`/`aheadFlag`, `verdict`, `reason`, `correlatingEvent`, `errors`.

   Classification lives in `scripts/lib/deploy-beacon.ps1` (covered by `scripts/deploy-beacon.smoke-test.ps1`, which replays all four real 2026-08 incidents as regression fixtures) specifically so it is tested code rather than prose re-derived here on every run. **Use its `verdict` — do not re-derive your own from the raw fields.** If the classifier itself fails to run, that is an ALARM (can't-verify is not healthy); fall back to `Get-ScheduledTaskInfo -TaskName "ORA Command Center - Mirror Deploy"` for the raw values and say plainly in the Notion row that the classifier was unavailable.

   **Why a beacon exists at all** (incident 2026-08-03): `deploy-mirror.ps1` reports failures from a `try/catch`, which only fires when the script THROWS. Three runs in the week of 08-01 instead returned `3221225786` (`0xC000013A` = `STATUS_CONTROL_C_EXIT`) — the process was KILLED, so the catch never ran, `Send-DeployFailureAlert` never fired, and `data/outbox/` (its own can't-send fallback) recorded nothing. The script now stamps `data/_state/mirror-deploy-beacon.json` as `running` at start and `completed` at its exit path; a run that was killed leaves it stuck at `running`. Run duration was evaluated as a detector and REJECTED — the three real kills lasted 4s, 96s, and several hours, which no threshold separates from healthy 5–19 minute runs.
5. Classify — **the `verdict` from step 4 decides this.** Verdict meanings:
   - `HEALTHY` — rc=0 and this run wrote a fresh success beacon.
   - `RUN_IN_PROGRESS` — the run is STILL EXECUTING right now (`lastTaskResult` = `267009` = `0x00041301` = `SCHED_S_TASK_RUNNING`). **Not an alarm, and not a result at all yet** — nothing can be said about this run's outcome until it finishes, and the next check classifies it. Do NOT describe it as killed, benign, or healthy-so-far in the Notion row; say the run was in flight at check time and give the elapsed minutes from `reason`. Added v1.5 after the 2026-08-09 09:08 check reported a healthy 8-minute-old run as "Run was killed (rc=267009) by machine lifecycle" — the classifier had only an rc=0 branch and an everything-else-is-a-kill branch, and 267009 is neither. (That run went on to fail legitimately at 09:11:58 on a wrangler timeout, which is a *different* finding and classified correctly as `ALARM_SCRIPT_FAILED`.) A `runEndedAt` of `null` is EXPECTED and correct here — an in-flight run has no completion event yet, and v1.5 stopped borrowing the previous run's.
   - `ALARM_RUN_STUCK` — still executing, but past the 90-minute threshold (`$script:MirrorRunStuckThresholdMinutes`). **Alarm.** Healthy runs take 5–19 minutes and the task fires hourly, so this is wedged, not working, and the mirror is not advancing. This exists so `RUN_IN_PROGRESS` cannot become a permanent silence: if the scheduler service dies mid-run, `lastTaskResult` can sit at `267009` indefinitely. Note in the email that the deploy-timeout work on branch `fix/deploy-mirror-deploy-timeout` may be the relevant fix.
   - `BENIGN_INTERRUPTED` — killed mid-run, with a power/session event within 90s of the run's end that explains it (reboot, Modern Standby transition). **This is NOT an alarm.** This machine reboots near-daily and enters Modern Standby ~20x/day; the next hourly fire re-bakes. Record it in the Notion row with the `correlatingEvent` and stay silent.
   - `BENIGN_KILLED_AFTER_COMPLETION` — rc is a kill code, but **this run's own** beacon already recorded `outcome=success`, so the deploy published before the process died and only teardown was lost. **Not an alarm, and the mirror is NOT stale** — say so explicitly in the Notion row, because the reflex on any kill code is to assume the cycle was discarded (which is correct for every *other* kill verdict — see the 2026-08-03 case in `reference_mirror_deploy_0xc000013a_is_usually_benign.md`, where a kill silently threw away a completed bake). What separates this one is that the success beacon is written *after* `wrangler deploy` returns 0. **Do not tell the reader to look for a `Send-DeployFailureAlert` email — the script did not throw and none was sent.** This verdict is gated on the beacon alone, never on event correlation, so it cannot absorb kills the way a widened correlation window would.
   - `ALARM_UNEXPLAINED_KILL` — killed with nothing to explain it. **Alarm.** Three cases so far: 2026-08-01 13:01:37 (System log had zero events 12:58–13:05), 2026-08-03 20:05:26, and 2026-08-04 11:00:01. **The third one initially reported as `ALARM_SCRIPT_FAILED`** because the run was killed 28s in, before it could write a beacon, and the classifier read the *previous* hour's beacon as this run's — fixed in v1.4; fixture 3d in the smoke test is the regression guard. Per the memory file's own instruction, three unexplained kills means the "usually benign" framing there is now due for review.
   - `ALARM_SILENT_INCOMPLETE` — rc=0 but the script never reached its exit path, or wrote no beacon for this run. **Alarm** — Windows says success and the script disagrees; nothing detected this before v1.2.
   - `ALARM_SCRIPT_FAILED` — the script threw and already self-alerted. **Alarm**, but note in the email that a `Send-DeployFailureAlert` mail should also have arrived; if it did not, the send path is itself broken and that is the bigger finding. **This verdict now requires a beacon belonging to THIS run** (v1.4) — before that fix a stale beacon could trigger it on a run that never threw, which sent the reader hunting a send-path outage that did not exist. That freshness gate is what makes the "bigger finding" advice above trustworthy; do not relax it.
   - `INDETERMINATE` — no readable beacon. Expected ONLY for runs predating the v1.2 rollout (2026-08-03); after the first post-rollout deploy, a persistent `INDETERMINATE` means the beacon is not being written — treat as ALARM.

   The legacy conditions below still apply on top of the verdict:
   - HEALTHY: `LastTaskResult == 0` AND `LastRunTime` within the last ~3 hours (task fires hourly; allow scheduler jitter). A nonzero drift count BY ITSELF is NOT an alarm — it just means new commits landed on origin since the last successful hourly pull+bake and will resolve on the next hourly fire (the script pulls to HEAD every run).
   - ALARM if ANY of: the step-4 `verdict` is one of the four `ALARM_*` values · `LastRunTime` older than ~3 hours during 07:00–20:00 ET (the task should have fired since) · working tree shows an entry the step-3 tests classify as FLAG (including a stuck merge/rebase marker). An entry the step-3 tests classify as BENIGN is NOT an alarm — note it in the Notion row with its verification output and stay silent.
   - **Superseded in v1.2:** "`LastTaskResult != 0` is automatically an ALARM" was the v1.0/v1.1 rule and it over-fires. A non-zero result now alarms only when the classifier cannot explain it. Do not reinstate the blanket rule — on this machine it would fire on ordinary reboots and train the reader to ignore the alert. Equally, do NOT widen the 90s correlation window to make more kills look benign; that is the failure direction that silences the check permanently (guarded by scenarios 2g/2i/3c in the smoke test).
   - **Ahead-of-origin: read `aheadFlag.severity` from step 4's classifier — do NOT re-derive this from the raw `gitAhead` count.** Three tiers, and the threshold lives in tested code (`$script:MirrorAheadEscalationThreshold` in `scripts/lib/deploy-beacon.ps1`, guarded by smoke-test cases 4c–4m), not in this file:
     - `OK` — not ahead. Nothing to report beyond the count.
     - `FLAG` — ahead, but below the threshold. Report in the Notion row with the commit list (`git log origin/main..HEAD --oneline`) and **stay silent — no alarm email.** This is the EXPECTED steady state, not a defect: `ora-lease-snapshot-refresh` auto-commits `data/snapshots/portfolio.json` up to 3x/weekday and is instructed never to push. Emailing here would over-fire daily and train the reader to ignore the alert — the same failure that got the blanket `rc != 0` rule rolled back in v1.2.
     - `ESCALATE` — at or past the threshold. **This IS an alarm email** (ggoldberg only, COM path), alongside the Notion row. Quote `aheadFlag.reason` verbatim and name the commits.
     Report the threshold using the `threshold` field the classifier returns; never hardcode the number in the Notion row. Superseded in v1.3: "escalate only if it persists across runs or exceeds a handful of commits" — "a handful" was never a threshold, and it re-derived classification in prose on every run, which is exactly what step 4's doctrine forbids. Never push the commits yourself regardless of tier; the no-push rule and this threshold are coupled (see the constant's comment before changing either).
   - If `Get-ScheduledTaskInfo` or the git commands themselves error out (repo moved, task renamed/deleted, etc.) — treat that as an ALARM too ("can't verify" is not "confirmed healthy"). Never fabricate a HEALTHY verdict from incomplete data.
