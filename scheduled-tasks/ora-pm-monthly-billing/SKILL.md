## Step 0 — run date, run id, once-a-month guard (FIRST action)

Compute once and reuse:
- RUN_DATE = `powershell -NoProfile -Command "Get-Date -Format 'dddd yyyy-MM-dd'"`. This is host-local time, the same clock trigger-billing.ps1 uses to pick the month it bills; Git Bash `date` can silently return UTC on this host. HOST_MONTH is its `yyyy-MM` part and DAY is its day of month.
- RUN_ID = `billing-` followed by `date -u +%Y%m%dT%H%M%SZ`, a hyphen and `$RANDOM` (two sessions in the same second must not share an id).

Why (root-caused 2026-11-05): the cron fires on the 1st, 2nd and 3rd (`10 11 1-3 * *`). The desktop scheduler consumes a slot when it dispatches the session, not when the run ends. On 2026-11-01 the 11:10 slot fell while the laptop slept; the catch-up session was spawned at 15:11 ET and the app was quit 4 seconds later, so lastRunAt advanced with no run, no email and no billing. (The ora-pm database had been paused since 10-12, so that run would have failed anyway; a run that reaches the endpoint and fails is reported, never retried.) The 2nd and 3rd exist only to recover a fire that never reached the script. The guard below makes the script run at most once per calendar month (US/Eastern).

python C:/Users/Owner/.claude/scheduled-tasks/_shared/block-sentinel.py claim --task ora-pm-monthly-billing --block main --run-id <RUN_ID> --period month --ttl-min 44640

- Exit 11 with the JSON's `record.runId` equal to your RUN_ID: you already hold the claim (the command ran twice). Treat it as exit 0.
- Exit 11 otherwise: a claim for this month exists and was never closed. Do not run the script, and call neither `complete` nor `fail`, because you do not own the claim.
  - `ageMin` under 60: another fire may be live. If DAY is 1 or 2, report a NORMAL skip and stop; a later slot re-checks.   - `ageMin` 60 or more: an earlier fire claimed the month and died before closing it, possibly mid-script. Do NOT retry: an interrupted money-moving run needs a human look. Send one email under Step 1 item 4's send rules, subject `[ACTION] ora-pm monthly billing — earlier fire never finished, not retried`, quoting the claim record (runId, claimedAt) and the re-arm steps.
  - Re-arm steps, for a human after checking this month's charges in ora-pm: `python C:/Users/Owner/.claude/scheduled-tasks/_shared/block-sentinel.py fail --task ora-pm-monthly-billing --block main --run-id <that runId> --period month --error "cleared after review"`, then this task's Run now. ## Step 1 — run the trigger

Run the ora-pm monthly billing trigger by executing the EXISTING, already-tested PowerShell script — do not re-implement its logic, do not modify it:

powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\Owner\ora-pm\scripts\trigger-billing.ps1"

Run it with the Bash tool's maximum timeout (600000 ms): the drain loop can take up to 8 calls of 60 s each. If the call times out or is killed after it started, it counts as invoked: close `complete` in item 5 and use the [ACTION] subject. Only a call that never started counts as "never started".

What this script does (for context only — you are invoking it, not reproducing it):
- POSTs to the deployed ora-pm Cloudflare Pages Worker's /api/cron/monthly-billing, authenticated with a Bearer token read from $env:ORA_PM_CRON_SECRET (User-scope env var on this machine, matches the CRON_SECRET Cloudflare Pages secret).
- Charge posting is a single bulk upsert with ON CONFLICT DO NOTHING on idempotency_key — a re-run or a retry cannot double-post the same charge.
- Drains the endpoint's `remaining` count in a bounded loop (MAX_INVOCATIONS=8, AUTOPAY_BATCH_LIMIT=8 leases/call = 64 autopay debits/run cap). Currently 0 leases are autopay-eligible in production (enrollment isn't reachable from the tenant portal yet — OI-068), so only the charge-posting path is exercised on this fire.
- Breaks loudly and exits non-zero if `remaining` fails to decrease between two calls (a lease whose Stripe call fails deterministically every attempt would otherwise re-occupy the same batch slot for the whole run) — this is a real failure, not a transient one; do not silently retry past what the script itself does.
