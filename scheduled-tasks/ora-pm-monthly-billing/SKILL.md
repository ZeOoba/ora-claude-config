## Step 0 — run date, run id, once-a-month guard (FIRST action)

Compute once and reuse: RUN_DATE = `date '+%A %Y-%m-%d'`; RUN_ID = `billing-` followed by `date -u +%Y%m%dT%H%M%SZ`.

Why (root-caused 2026-11-05): the cron fires on the 1st, 2nd and 3rd (`10 11 1-3 * *`). The desktop scheduler consumes a slot when it dispatches the session, not when the run ends. On 2026-11-01 the 11:10 slot fell while the laptop slept; the catch-up session was spawned at 15:11 ET and the app was quit 4 seconds later, so lastRunAt advanced with no run, no email and no billing. The 2nd and 3rd exist only to recover a fire like that. The guard below makes the script run at most once per calendar month (US/Eastern).

python C:/Users/Owner/.claude/scheduled-tasks/_shared/block-sentinel.py claim --task ora-pm-monthly-billing --block main --run-id <RUN_ID> --period month --ttl-min 44640

- Exit 10: this month's billing step already ran. Do not run the script, do not email. Report a NORMAL skip naming the record's runId; it is not a miss.
- Exit 11: a claim for this month exists and was never closed. Do not run the script, and call neither `complete` nor `fail` (you do not own the claim). If the JSON's `ageMin` is under 60, another fire is live: report a NORMAL skip and stop. If it is 60 or more, an earlier fire claimed the month and died before closing it, possibly mid-script. Do NOT retry: an interrupted money-moving run needs a human look. Send one email under step 4's send rules with subject `[ACTION] ora-pm monthly billing — earlier fire never finished, not retried`. The body quotes the claim record (runId, claimedAt) and says: check this month's charges in ora-pm; to re-arm after review, run `python C:/Users/Owner/.claude/scheduled-tasks/_shared/block-sentinel.py fail --task ora-pm-monthly-billing --block main --run-id <that runId> --period month --error "cleared after review"`, then start the run manually.
- Exit 0: claim held; continue to Step 1. If the JSON's `stateFileError` is not null, the guard is degraded: quote that string in the summary email body.
- Any other exit: tooling failure. Fail open per `_shared/README-DOUBLE-FIRE-GUARD.md`: continue to Step 1 (the endpoint is idempotent, see below) and quote the exit code and output in the summary email body. Never read a code other than 10 or 11 as "already done".

The 31-day TTL is deliberate, unlike other tasks' 30–45 minutes: an unclosed claim must hold for the rest of the month rather than expire into an automatic re-run. A scheduled fire never passes `--force`.

## Step 1 — run the trigger

Run the ora-pm monthly billing trigger by executing the EXISTING, already-tested PowerShell script — do not re-implement its logic, do not modify it:

powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\Owner\ora-pm\scripts\trigger-billing.ps1"

What this script does (for context only — you are invoking it, not reproducing it):
- POSTs to the deployed ora-pm Cloudflare Pages Worker's /api/cron/monthly-billing, authenticated with a Bearer token read from $env:ORA_PM_CRON_SECRET (User-scope env var on this machine, matches the CRON_SECRET Cloudflare Pages secret).
- Charge posting is a single bulk upsert with ON CONFLICT DO NOTHING on idempotency_key — a re-run or a retry cannot double-post the same charge.
- Drains the endpoint's `remaining` count in a bounded loop (MAX_INVOCATIONS=8, AUTOPAY_BATCH_LIMIT=8 leases/call = 64 autopay debits/run cap). Currently 0 leases are autopay-eligible in production (enrollment isn't reachable from the tenant portal yet — OI-068), so only the charge-posting path is exercised on this fire.
- Breaks loudly and exits non-zero if `remaining` fails to decrease between two calls (a lease whose Stripe call fails deterministically every attempt would otherwise re-occupy the same batch slot for the whole run) — this is a real failure, not a transient one; do not silently retry past what the script itself does.

After running:
1. Read the script's stdout for each invocation's `posted=... skipped=... errors=... chargeErrors=... autopayErrors=... remaining=...` line.
2. Report a one-line summary: total posted, any chargeErrors/autopayErrors, final `remaining` (should reach 0).
3. If the script exits non-zero, or `remaining` never reaches 0, flag this loudly — do not report success. This is a money-moving job; a partial or failed run needs a human look, not a quiet retry next month.
4. Send ONE summary via Outlook COM (C:\Users\Owner\.claude\scheduled-tasks\_shared\send-via-outlook.ps1 — the sole send path) to ggoldberg@oxfordra.net ONLY (no cc). Subject: "ora-pm monthly billing — <posted> charges posted, remaining=<N>" (flip to "[ACTION]" prefix on any non-zero exit or nonzero final remaining). On send exit 2 or 4: retry once; if it still fails, do not halt — automation-health-monitor will catch a missed send, but note the failure in the run output anyway. On exit 5 or 6 (or any code other than 2 or 4) do NOT retry: flag it loudly in the run summary and in the failure record named above, and never resend (exit 6 = send state unknown — the message MAY have gone out), per rules.md §2.
5. Close the claim. Only a run that got exit 0 in Step 0 does this, with the same RUN_ID, on ONE line:
   - The script was invoked, whatever its exit code or final `remaining`: `python C:/Users/Owner/.claude/scheduled-tasks/_shared/block-sentinel.py complete --task ora-pm-monthly-billing --block main --run-id <RUN_ID> --period month --email-sent-at <ISO8601 send time>`. Leave out `--email-sent-at` if the send failed or ended in exit 6. COMPLETE here means "this month's money-moving step was attempted", not "billing succeeded"; the email subject carries the outcome. This deliberately differs from tasks that close `fail` on a bad run: a failed or partial billing run gets a human look, never an automatic retry on the 2nd or 3rd.
