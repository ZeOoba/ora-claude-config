What this script does (for context only — you are invoking it, not reproducing it):
- POSTs to the deployed ora-pm Cloudflare Pages Worker's /api/cron/critical-dates-alerts and /api/cron/delinquency-check endpoints, authenticated with a Bearer token read from C:\Users\Owner\ora-pm-cron\cron-secret.txt.
- Logs every call (counters only, PII-redacted) to C:\Users\Owner\ora-pm-cron\cron.log.
- When either endpoint's JSON response carries a non-null `email` field, sends that digest via the canonical Outlook-COM sender to ggoldberg@oxfordra.net ONLY. The script is the sole sender — never draft or send a duplicate email yourself for this task (the one exception is the fallback alert in step 4 below).
- OI-278 (2026-09-13): while delinquency-check returns `payments_feed_absent: true`, the script tracks that in C:\Users\Owner\ora-pm-cron\payments-feed-state.json and emails the PAYMENTS FEED ABSENT digest only on the first absent run, every 7 days after, or whenever late_fees_posted > 0. Other days it logs `SEND SUPPRESSED reason=suppressed-repeat tracked=OI-278` instead of sending. That is expected and is NOT a send failure. When the feed returns, it also sends a one-time "PAYMENTS FEED RESTORED - OI-278 can be closed" email.
- A POST failure is a RUN FAILURE, never a retry-later condition: any non-2xx from either endpoint (redirects are not followed), no HTTP response at all, or a 2xx whose body is not JSON. This task runs weekly (cron `40 9 * * 1`), so the next attempt is 7 days out, and critical-dates-alerts has no other trigger (the off-host GitHub backup covers delinquency-check only). For each failed endpoint the script reads the error body only to find a Cloudflare 1xxx code and logs that code, never the body (it can carry tenant data): `cf_error=1016 (Supabase project likely PAUSED ...)` when a 1016 sits inside the app's JSON error, `cf_error=<code> (... failing layer not identified)` for any other code. It then emails ONE `CRON FAILURE - [ORA PM] ...` alert via the canonical Outlook-COM sender to ggoldberg@oxfordra.net ONLY, prints a `RUN FAILED:` line ending `failure-alert=SEND OK` or `failure-alert=SEND FAILED exit=<n>`, and exits 1. A digest send failure (`SEND FAILED` on an endpoint's line) is logged and does not change the exit code.
