## 3a. fleet-status.py verdict recalibration (2026-07-14)
The old VERDICT logic flagged ATTENTION on ANY never-ran task, ANY expired one-time task, and the ALL-TIME cumulative throttle-skip count. On a fleet spanning daily→annual cadences plus one-time tasks, that's structurally unable to ever show OK (a quarterly task is "never-ran" for up to 3 months by design; a successfully-completed one-time task stays "expired" forever; `recordedSkips` never resets). Recalibrated: never-ran only flags if a RECURRING task's `createdAt` age exceeds a cadence-aware buffer inferred from its cron fields (`cadence_buffer_days()` — 3d daily-ish / 10d weekly-ish / 40d monthly-ish / 120d quarterly+); expired one-time only flags if it never fired or never auto-disabled (a real miss, not a normal completion); throttle skips only count within the last 24h. Same-time collisions unchanged. First real-world result: 9 never-ran + 3 expired + 36 all-time skips collapsed to ONE genuine finding — `ora-tenant-db-dedup-remediation` truly expired before ever firing. 13 new tests in `test-fleet-status.py` (didn't exist before — subprocess-driven against a synthetic `--registry --json`, no `datetime.now()` mocking needed since fixtures are computed relative to wall-clock at test-run time).

## 3c. Stuck-Session Watchdog (added 2026-07-15) — mirror-image of fleet-deadman.ps1
- **`maintenance/stuck-session-watchdog.ps1`** — kills scheduled-task-fired `claude.exe` sessions that have run past 90 minutes (default, `-ThresholdMinutes` override). Runs from Windows Task Scheduler ("ORA Stuck-Session Watchdog", every 30 min) independent of the Claude fleet, so it fires even if the fleet itself is wedged. `fleet-deadman.ps1` watches for the fleet going SILENT; this watches the opposite failure mode — a session that fired and never finished.
- **Why:** no scheduled task in this fleet has an overall session timeout (retries are bounded per-step only, e.g. ora-health-guard's "retry Notion at most twice"). Confirmed same-day: 3 stuck `ora-health-guard`/`ora-site-exposure-probe` sessions each spawned 4 separate branches of nested child processes (~14-15 procs apiece) when killed — consistent with connector/subprocess handles opened and never released. A 16-process batch the previous evening showed the same pattern. Nothing existed to stop either one.
- **Detection** (`maintenance/stuck-session-watchdog-lib.ps1`, `Get-KillCandidates` — pure function, unit-tested against synthetic fixtures in `test-stuck-session-watchdog.ps1`, 9/9 pass, never against real processes): a scheduled-task session has no `--resume=` flag (fresh invocation) and a long CommandLine (excludes the bare desktop-app shell, ~84 chars). **Hard safety line: any process carrying `--resume=` is never touched**, regardless of age — it may be an active interactive conversation. Caught a real PowerShell single-element-array-unwrap bug in testing (would have silently no-op'd whenever exactly one session was stuck) — fixed before this ever ran live.
- **Alarm:** file-only (`Desktop\STUCK-SESSION-ALERT.txt` + `maintenance\stuck-session-watchdog.log`) when it actually kills something; silent log-only on a clean run. No email, no toast — same convention as fleet-deadman.ps1. Manual dry run: `-WhatIf` (logs what would be killed, kills nothing).
- **Open follow-up:** this cleans up after the hang, it doesn't prevent it. The actual fix is adding a timeout to whichever specific step in `ora-health-guard`/`ora-site-exposure-probe` (or elsewhere) is hanging — not yet root-caused to a single step, just to "some step in Block B or C lacks one." Worth a dedicated investigation next time the alert file fires with a fresh, still-diagnosable process tree.
- All three guards fail OPEN on any internal error or unsimulatable edit shape — a bug here must never block a legitimate write (same posture as every other PreToolUse guard in this stack). Full guard inventory + TDD suites: `~/.claude/hooks/*.py` + `~/.claude/hooks/tests/test-*.py` (one test file per guard). ## 3d. Master Workbook single-writer protocol (RATIFIED 2026-07-25)
- **Why:** the live ORA Master Workbook's own "Claude Log" sheet showed ~140 turns on 2026-07-24 from what read as multiple uncoordinated agent sessions writing to the same file — a botched rent-roll sort that corrupted formula references (Turns 108/111/112, caught in 115) and a debt-balance cell (`External Loans Summary!E10`) that flip-flopped 5× in immediate succession (Turns 132–136). Unlike `ora-skills` or the scheduled-task registries, this workbook had no analogous single-writer gate — the one file CLAUDE.md names as FIRST for firm figures. Full incident + rationale: memory `project_master_workbook_no_single_writer_2026-07-24.md`, `project_master_workbook_single_writer_proposal_2026-07-25.md`.
- **NOT a hard lock.** [[feedback_fail_open_over_mutex_for_fleet_gates]] is the ratified house default — a crashed session holding a hard claim on the ONE master workbook would wedge every other session and every scheduled brief/reconciliation job, a worse failure than an occasional missed collision.
- **Scope:** applies only before STRUCTURAL writes (sorts, row insert/delete, mass formula rewrite — the actual failure category in Turns 108/111/112) to the 4 highest-blast-radius sheets: **Master Tenant Rent Roll, External Loans Summary, Property NOI, Portfolio Summary.** Single-cell value edits (the vast majority of turns, e.g. one lease-date correction) are lower blast-radius and skip the claim entirely, matching Engineering OS's existing blast-radius calibration.
- **Claim protocol (documented convention, no shared script — mirrors the ora-skills `git log -1` pattern):** before a STRUCTURAL write to one of the 4 sheets above, (1) stamp `{sessionId, startedAt, expiresAt}` — TTL ~15 min — into a dedicated `_active_sessions` sheet in the workbook; (2) read the Claude Log's own last row — if its timestamp is within the TTL window and its logged actor isn't this session, that's a second affirmative signal: STOP and surface the conflict rather than silently proceeding or overwriting. Two independent affirmative signals are required before treating a write as unsafe — absence of information is never license to block.
- **Fail-open:** if the claim area is unreadable, malformed, or the check itself errors, proceed anyway (log a warning to the Claude Log) rather than block.
- **On completion:** clear (or let expire) the claim; log the turn to Claude Log as already happens.

## 3e. Cross-session claim/broadcast (RATIFIED 2026-07-25, `task_17998414`)
- **Why:** `reference_concurrent_session_duplicate_hardening_work.md` logs 6 recorded collisions (2026-07-16 through 2026-07-24) of concurrent sessions independently duplicating work on a shared subsystem that has no per-path single-writer rule — narrower than a file-level conflict (the sessions may never touch the same file), so git alone can't catch it. The prior mitigation (manually run `git worktree list` + check `list_sessions`) already failed to catch the worst incident. Full design: `docs/superpowers/specs/2026-07-25-cross-session-claim-broadcast-design.md`.
- **Mechanism:** `hooks/lib/claim_work.py claim <slug> "<description>" [--paths <p>...]` writes `hooks/active-work/<slug>.json` (session id from `$CLAUDE_CODE_SESSION_ID`, atomic rename, one file per claim — no shared file to race, same argument as `fleet-session-hook.py`'s 2026-07-24 per-session-file rewrite). A `SessionStart` hook, `hooks/active-work-broadcast.py`, reads all non-expired claims and surfaces any NOT belonging to the starting session via `additionalContext` — automatic, replacing the manual pre-check for this signal.
- **FILE-LEVEL collisions (ADDED 2026-07-26).** Slugs are work-TYPE scoped, and the SessionStart broadcast only reaches sessions that start *after* a claim. On 2026-07-26 **four** sessions edited `scheduled-tasks/ora-weekly-hygiene/SKILL.md` inside a few minutes and none was warned: two held honest claims under *different* slugs (`ora-weekly-hygiene-spec`, `repo-housekeeping`), and every claim was made mid-session, so no broadcast could reach anyone already running. Two independent gaps, both now closed:
  - `claim_work.py` claims carry optional `paths` (files **or directories** — a directory covers everything beneath it). `claims_touching()` answers "who else claims this path".
  - `shared-checkout-guard.py` (already `PreToolUse`-bound, so **no `settings.json` change**) emits a `SAME-FILE COLLISION` warning on the file being edited, OR-ing two evidence sources: other live sessions' provenance `touched-files.txt` (automatic, needs no discipline, but only after their first edit) and claim-declared paths (covers the pre-first-edit window). It runs **before** the clean-status early return — two sessions can collide on a committed file in an otherwise-clean repo.
  - Bounds that matter: a 90-min recency window on provenance (an abandoned touch is not "actively working"), dedup keyed on the *identity set* of colliding sessions (not the rendered message — liveness `status` flips working↔idle constantly and made it re-fire on nearly every edit), markers written only **after** delivery, and hard caps (512 claim files, 64 KB each) since the claims dir is world-writable, never pruned, and now read on the Edit hot path. Cost ~+14 ms per Edit/Write in a shared repo.
  - Untrusted-text posture: claim descriptions and liveness fields reach **model-visible** `additionalContext`. Descriptions are sanitized *and* explicitly fenced as untrusted; `status` is allowlisted (`working`/`idle`/`ended`, else dropped). Do not interpolate a new claim/liveness field into that message without the same treatment.
- **NOT a hard lock** (same doctrine as §3d): 2-hour TTL, fail-open on any error — the `PreToolUse` same-file check above **never blocks**, it only adds context. `release <slug>` is best-effort, not required — an unreleased claim just ages out.
- **`claim` REFUSES a live collision (CHANGED 2026-08-09).** It used to overwrite another session's live claim unconditionally and print the WARNING *after* the decision was already made, so the warning could only ever document a clobber, never prevent one — recorded twice (OI-075's `b5d8615c`; and 2026-08-09 ~14:27, a claim destroyed two minutes after it was made while its owner was actively removing worktrees, restored by hand-rewriting the JSON). Now: **exit 3, nothing written**, unless `--force` (alias `--steal`). The refusal message is path-aware (tri-state: overlap / provably disjoint / undeterminable — absent `--paths` reads as *undeterminable*, never as disjoint) and prints the holder's `host_session_id` so the reply is "message them", not "clobber them". `--force` preserves the displaced claim in the new claim's `prior_claim`; `claim_work.py restore <slug>` puts it back (one command, replacing the manual JSON rewrite). This does **not** contradict the fail-open doctrine above, which is about the READ path: no hook invokes this CLI (hooks import `read_active_claims`/`claims_touching`/`renew_claim`), so nothing on the Edit/Write hot path can be wedged by an exit code, and `--force` is unconditional so a crashed session's claim can never lock anyone out. Malformed/unattributable claim files still fail **open** (they cannot deny a slug).
- **Unattended (scheduled-task) claims — reserved `sched-` namespace (RATIFIED 2026-09-07, Gabriel).** The refusal path above resolves to "message the holder", which is impossible when the holder is a scheduled task: on 2026-09-07 an unattended task held `repo-housekeeping`, committed into `ora-skills` main mid-session, and was absent from all 445 peer sessions, so `send_message` had no target. Ruling: **an unattended task claims under a `sched-` prefixed slug**, which (i) gets a short **30-minute TTL** (`SCHED_TTL_MINUTES`) instead of the 120-minute default, so a dead run's claim ages out before it can block a live person, and (ii) makes force-takeover **routine, not a transgression** — the refusal message now says so explicitly rather than leaving each session to rediscover it. Verify the holder's work actually landed before forcing (`git log`/`git status` on the claimed paths), then force. **The prefix is a HYPHEN, not a colon:** the slug IS the filename (`<slug>.json`) and `:` is illegal on Windows, so `sched:` would be silently mangled by `_safe_filename()` into a different slug than the caller asked for — there is a test pinning this. TTL selection is `min(caller_ttl, 30)`, so a caller already asking for a shorter window is never widened. Implemented in `hooks/lib/claim_work.py` (`is_sched_slug()`, `_effective_ttl()`); 11 tests in `hooks/tests/test-claim-work-lib.py` (215 total). Note the ordinary path is UNCHANGED — an interactive session's claim still gets 120 minutes and still refuses without `--force`. Precedent for preferring a distinct slug over a takeover when paths do not overlap: `claim_work.py` prints that advice itself, and it was the right call on 2026-09-07 (`repo-housekeeping` covered only `CLAUDE.md`, so the ora-skills work took `repo-housekeeping-oraskills-sweep` and both claims stayed visible).
  - **The gate covers ALL FOUR write paths, not just `claim`** — the adversarial pass showed a partial gate is no gate: `release <slug>` then `claim <slug>` reached the clobber at exit 0, with no refusal and nothing restorable. So `release` now refuses to delete a claim that isn't yours, or one still carrying a takeover's undo record (it points at `restore` instead — the undo lives *inside* the claim file, so releasing destroyed the only copy). `restore` takes the same gate as `claim`. Invariant to hold onto: **every path that can displace a live claim refuses by default, reports what it would displace, and preserves it.**
  - **Fail-open means "does not BLOCK you", never "does not PRESERVE what it overwrote."** An unattributable claim is still overwritten, but its metadata is now kept in `prior_claim` — the first cut discarded it irretrievably, re-opening the unrecoverable clobber through the fail-open branch. Relatedly `own_session_id()` normalizes at the source: `CLAUDE_CODE_SESSION_ID="  "` used to be stored verbatim, so a *legitimate* session silently had no collision protection at all and no symptom it could observe.
