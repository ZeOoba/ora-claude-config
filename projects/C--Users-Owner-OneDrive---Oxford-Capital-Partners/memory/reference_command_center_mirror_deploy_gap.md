**Finding (2026-07-09):** Gabriel asked to see the live command center and it did not reflect the just-merged Mission-Control retokenization (PRs #186–#191 — tokens/fonts/radii/themes, KpiStat/TierBoard/Sidebar/Badge consumers, contrast fixes). Root cause: the local checkout at `C:\Users\Owner\oxford-command-center` was 7 commits behind `origin/main`. `scripts/deploy-mirror.ps1` (run hourly by the "ORA Command Center - Mirror Deploy" Windows scheduled task, see `scripts/register-mirror-task.ps1`) does `Set-Location $repo` and immediately bakes+builds+`wrangler pages deploy`s — **it never runs `git pull`**. So the hourly job kept redeploying stale pre-retokenization code with a fresh data snapshot ("STATIC · baked Nm ago" only reflects data freshness, not code freshness — easy to misread as "everything is current").

**Fix applied this session:** manually `git stash` (2 locally-modified files: `.claude/launch.json.example`, `package.json` — no conflict, stash popped clean) → `git pull --ff-only` (85 files, 7 commits) → `npm install` (3 new fontsource packages) → `npm run gate` (crashed via a Windows npm-wrapper segfault immediately after the test suite finished, 2/2 times — same failure signature as [[feedback_npm_test_intermittent_access_violation]]; all 37 test files showed passing, so ran `reconcile`/`warehouse:verify`/`warehouse:drift` directly instead of re-fighting the wrapper — all passed) → `scripts/deploy-mirror.ps1` → verified live via browser screenshot.

**Fixed (2026-07-09, PR #192, `fix(deploy): mirror deploy fast-forwards to origin/main before baking`):** `deploy-mirror.ps1` now does `git fetch origin` + `git pull --ff-only` before baking, and `throw`s (aborting the deploy) if the pull fails — diverged history or a conflicting dirty tree can no longer result in a silent stale deploy. Verified live 2026-07-09: local `oxford-command-center` main is 0 commits behind `origin/main`.

**Residual gap — CLOSED (2026-07-09):** the fix is fail-*loud*, not fail-*alerted* — `deploy-mirror.ps1` itself still has no logging/email/Notion write on failure, and the actual bake+deploy task (`scripts/register-mirror-task.ps1`, "ORA Command Center - Mirror Deploy") remains a native `Register-ScheduledTask` Windows job outside the dual-fleet registry **by design** — moving it into the MCP registry would trade reliable 24/7 execution for "only runs while Claude Desktop is open" (confirmed via the `create_scheduled_task` tool description), a straight regression. Gabriel approved wiring visibility in without that migration. Closed by registering a separate lightweight checker task, `ora-command-center-mirror-drift-check` (CC/MCP registry, weekdays 10:44 AM ET) — it reads `Get-ScheduledTaskInfo` on the native task plus git drift/tree state each run, stays silent when healthy (LastTaskResult==0 and a run within ~3h), and emails `ggoldberg@oxfordra.net` only (COM path) on a real alarm. It's now covered by `automation-health-monitor`'s heartbeat since it lives in `list_scheduled_tasks`. Known limitation baked into its own prompt: this checker is itself desktop-app-gated, so it's a business-hours sampling layer on top of the native task, not a 24/7 guarantee — acceptable since the underlying failure mode (a genuine git divergence/conflict) doesn't self-heal on its own anyway and just needs same-day human attention.

**Follow-up (2026-07-10): git-fetch 128 auth failures were being misclassified as the offline-suppressible signature — [PR #202](https://github.com/ZeOoba/oxford-command-center/pull/202), MERGED 2026-07-10.** Test-OfflineSignature only ever checked the throw-message shape (`^git (fetch|pull)\b`), not the actual git error text, so a genuine gh.exe credential/auth failure (recurred multiple times today) produced the identical `"git fetch origin failed (128)"` shape as a real network outage and got silently folded into the same suppression path — never alerting with the real fix. deploy-mirror.ps1 now captures real git stderr, classifies it via a new `Test-GitAuthFailureSignature` predicate, attempts one self-heal retry via the documented Credential Manager fallback (see [[reference-github-credential-path]]), and if that also fails throws a distinctly-prefixed `"GIT AUTH FAILURE (128): ..."` reason that Test-OfflineSignature deliberately never matches — so a non-self-healing credential problem always alerts immediately with the exact fix embedded, instead of going quiet. Also swapped the post-fetch `git pull --ff-only` for `git merge --ff-only origin/main` (avoids a second network/credential call). Smoke test: 33/33 assertions pass. Built + reviewed in worktree `.claude/worktrees/mirror-deploy-git-auth`.

**Belt-and-suspenders alerting inside deploy-mirror.ps1 itself — MERGED (2026-07-09), [github.com/ZeOoba/oxford-command-center/pull/196](https://github.com/ZeOoba/oxford-command-center/pull/196), squash-merge commit `59b8e58`. Implemented on branch `mirror-deploy-alerting` (worktree `.claude/worktrees/mirror-deploy-alerting`): wraps the pipeline in try/catch, emails `ggoldberg@oxfordra.net` (COM, no cc) via the existing `send-via-outlook.ps1` on any failure (CRITICAL subject for the Access-gate case), falls back to `data/outbox/` if the send itself fails, always re-throws the original exception so `LastTaskResult` stays accurate for the checker task above. Local review (general-purpose subagent, not cloud — this repo wasn't opted into `/code-review ultra`) caught a real **Critical** bug in the first commit: passing the alert body as a native `-Body` argument to a child `powershell.exe` corrupts/breaks the send if the failure reason contains a `"` — silently degrades to the unwatched outbox with zero email, exactly defeating the point. Fixed via `-BodyFile` (same convention `server/brief/send.ts` already uses for the identical reason) in a second commit, which also extracted `Send-DeployFailureAlert` to `scripts/lib/deploy-alert.ps1` and added `scripts/deploy-mirror.smoke-test.ps1` — a permanent, run-by-hand regression test (this repo has zero Pester/`.Tests.ps1` coverage) that exercises the real function against a stub mailer. Building that smoke test surfaced two more real PowerShell footguns worth remembering generally (not specific to this file): (1) `-like` treats a backtick in the PATTERN as an escape character, not a literal — never build a `-like` pattern by interpolating untrusted/arbitrary content, use `.Contains()` for exact-substring checks instead; (2) a single-element array collapses to a bare scalar at BOTH the point a function's `Where-Object`/pipeline output is captured AND again at the caller's own assignment — wrapping with `@(...)` only inside the function is not sufficient, the call site needs `$x = @(Get-Thing)` too, or `$arr[0]` silently indexes a character/property of the collapsed scalar instead of the first element. One real end-to-end test send (via the actual `send-via-outlook.ps1`, clearly `[TEST]`-labeled) confirmed delivery before the `-BodyFile` fix landed; the fix itself was verified via the smoke test's stub (which reads `-BodyFile` the identical way the real mailer does), not a second real send.
