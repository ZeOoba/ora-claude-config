**Follow-up (2026-07-10): git-fetch 128 auth failures were being misclassified as the offline-suppressible signature — [PR #202](https://github.com/ZeOoba/oxford-command-center/pull/202), MERGED 2026-07-10.** Test-OfflineSignature only ever checked the throw-message shape (`^git (fetch|pull)\b`), not the actual git error text, so a genuine gh.exe credential/auth failure (recurred multiple times today) produced the identical `"git fetch origin failed (128)"` shape as a real network outage and got silently folded into the same suppression path — never alerting with the real fix. deploy-mirror.ps1 now captures real git stderr, classifies it via a new `Test-GitAuthFailureSignature` predicate, attempts one self-heal retry via the documented Credential Manager fallback (see [[reference-github-credential-path]]), and if that also fails throws a distinctly-prefixed `"GIT AUTH FAILURE (128): ..."` reason that Test-OfflineSignature deliberately never matches — so a non-self-healing credential problem always alerts immediately with the exact fix embedded, instead of going quiet. Also swapped the post-fetch `git pull --ff-only` for `git merge --ff-only origin/main` (avoids a second network/credential call). Smoke test: 33/33 assertions pass. Built + reviewed in worktree `.claude/worktrees/mirror-deploy-git-auth`.

Building that smoke test surfaced two more real PowerShell footguns worth remembering generally (not specific to this file): (1) `-like` treats a backtick in the PATTERN as an escape character, not a literal — never build a `-like` pattern by interpolating untrusted/arbitrary content, use `.Contains()` for exact-substring checks instead; (2) a single-element array collapses to a bare scalar at BOTH the point a function's `Where-Object`/pipeline output is captured AND again at the caller's own assignment — wrapping with `@(...)` only inside the function is not sufficient, the call site needs `$x = @(Get-Thing)` too, or `$arr[0]` silently indexes a character/property of the collapsed scalar instead of the first element. One real end-to-end test send (via the actual `send-via-outlook.ps1`, clearly `[TEST]`-labeled) confirmed delivery before the `-BodyFile` fix landed; the fix itself was verified via the smoke test's stub (which reads `-BodyFile` the identical way the real mailer does), not a second real send. **New defect found + fixed (2026-07-26), [PR #240](https://github.com/ZeOoba/oxford-command-center/pull/240), MERGED same day (`2b121dc`). Local main fast-forwarded; fix live in the checkout for the next hourly run.** The 15:01:30 hourly run alerted `"Reason: From https://github.com/ZeOoba/oxford-command-center"` — a useless fragment, for what was actually a routine, successful 2-commit pull (repo was never diverged/dirty, just behind; fast-forwarded clean to `e7446cc`). Root cause: `deploy-mirror.ps1`'s git-fetch capture (`& git fetch origin 2>&1 | Out-String`) let Windows PowerShell 5.1 convert git's routine "From `<url>`" stderr progress header — printed on every *successful* fetch that has new commits to report, not just failures — into a terminating `ErrorRecord` under `$ErrorActionPreference = 'Stop'`, even through a `2>&1` merge. This discarded the script's own `"git fetch origin failed (N): ..."` throw wording entirely. Confirmed via reproduction in an isolated throwaway bare-repo harness (real fetch, real new ref-update content, same PowerShell 5.1 binary Task Scheduler uses) — `2>&1`/`2>$null`/`*>$null` on the PowerShell side all still throw; only routing through `cmd.exe` (whose own `2>&1` merges streams at the OS pipe level before PowerShell ever sees them) reliably avoids it. Fix: `Invoke-NativeCommandCapture` / `Invoke-GitFetchCapture` in new `scripts/lib/git-capture.ps1`, plus a permanent regression test (`scripts/git-fetch-capture.smoke-test.ps1`) built against real git behavior. Local review (general-purpose subagent) caught the identical latent bug shape in the `curl.exe` Access-gate verification call (this script's highest-stakes throw — detects a confidential bake being publicly exposed) — fixed in the same PR by routing it through the same shared function, plus a metacharacter guard on the shared capture function for future callers. **General PowerShell 5.1 lesson worth remembering beyond this file:** `$ErrorActionPreference = 'Stop'` converts ANY native-command stderr line into a terminating `ErrorRecord`, regardless of how the stream is redirected on the PowerShell side (`2>&1`, `2>$null`, `*>$null` — all still throw); only merging streams *inside* a `cmd /c "... 2>&1"` string sidesteps it, because PowerShell then only ever sees cmd.exe's own plain stdout.

**Alerting blind spot confirmed live (2026-07-27) — the in-script alerting CANNOT fire on a forcible kill; the drift-check task is the sole detector for that class.** The 10:00:01 run returned `LastTaskResult = 3221225786` (`0xC000013A` / `STATUS_CONTROL_C_EXIT`) — a *process termination*, not a script-level `throw`. Because the process was killed outright, the whole try/catch added in PR #196 (`Send-DeployFailureAlert`, the "24/7, not desktop-gated" belt-and-suspenders layer described above) never executed: no email, no `data/outbox/` fallback, nothing. `ora-command-center-mirror-drift-check` reading `Get-ScheduledTaskInfo` was the only thing that caught it. **Durable consequence: the two alerting layers are not redundant for this failure class — the in-script catch covers `throw`s, the drift-check task covers kills, and only the desktop-gated one covers kills.** Root cause that day was benign (Kernel-Power Event ID 109 shutdown transition at 10:35:47 killed the in-flight run; git side was spotless — drift 0, `git status --short` completely empty, HEAD `958402a`, no merge/rebase markers, so PR #192's fast-forward fix was working exactly as designed). A "contributing factor" hypothesis raised at alarm time — that the 30-min `ExecutionTimeLimit` was about to force-kill the run anyway at 10:30:01, five minutes *before* the shutdown, since `dist/` was untouched after 30 minutes — **was WITHDRAWN on the 11:00 evidence: the same tree/commit/code path baked and deployed in ~4 minutes** (`snapshot.json`/`macro.json` 11:00 → `build:mirror` output 11:03 → SW emit 11:04), and a genuine build/deploy stall does not clear itself between consecutive hourly fires with no intervening change. Sole cause was the shutdown. **Generalizable lesson: `dist/` being untouched at kill time proves only that the run didn't *reach* the write, not that it was stuck — a process killed while idle looks identical to one killed while grinding, and only the next clean run can tell them apart.** Resist promoting that ambiguity to a standing performance concern. Service impact was nil: a failed deploy leaves the prior Cloudflare Pages deployment serving, and `https://brain.oxfordra.net/` still returned 302 → the Access login host, so the gate held and no confidential bake was exposed — the only cost was one stale hourly cycle (`dist/` mtimes stuck at 09:00). **Diagnostic limitation found the same run:** the `Microsoft-Windows-TaskScheduler/Operational` event log is DISABLED on this machine (a 3-day `Get-WinEvent` query returned zero events), so the drift check can only ever read the current `LastTaskResult` snapshot and cannot distinguish a one-off from a third consecutive failure. Enabling it (`wevtutil sl Microsoft-Windows-TaskScheduler/Operational /e:true`) is a system-settings change — surfaced to Gabriel, not done autonomously. **`wevtutil sl` REQUIRES an elevated shell** — it writes to `HKLM`, so a normal (even Administrators-group) pwsh session returns `Failed to save configuration or activate log … Access is denied.`; Gabriel hit exactly this on 2026-07-27 because the command was handed over without the elevation prerequisite stated. Always pair it with "Run as administrator". Still not enabled as of 2026-07-27.
