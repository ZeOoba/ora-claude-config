**✅ RESOLVED 2026-08-15 (same session, Gabriel-directed follow-up "investigate and fix").** The predicted `settings.json` collision was real but manifested differently than first predicted: `2b9b419`/`4b8cb04` were NOT purely local-unpushed as originally stated — a `git merge-base --is-ancestor` check (not run the first time) showed both are ALSO ancestors of `origin/feat/model-canary-probe-step25` (pushed there independently of the live checkout, from a different session/clone). And a plain `git merge origin/main` into that branch reported **zero conflict markers** — clean by git's own accounting — but a clean line-based merge has no notion of JSON semantics: it silently produced a genuine duplicate, `scheduled-task-update-preguard.py` registered TWICE in `PreToolUse` (the paired `postguard.py` entry happened to land clean). Fixed in an isolated worktree (`fix/reconcile-canary-with-main`, off `origin/feat/model-canary-probe-step25`): merged `origin/main` in, found the duplicate via an exhaustive per-event JSON-signature scan (plus a duplicate-object-key scan, since `json.load` silently drops those), removed the redundant entry, independently reviewed and confirmed correct (post-fix file = main's settings.json + the branch's own intentional `enabledPlugins` change, nothing else), 49/49 hooks tests green, pushed directly to `origin/feat/model-canary-probe-step25` (`e6eccfb..fa1fc5c`). That branch now fully contains `origin/main` (`git merge-base --is-ancestor` confirms) — **and PR #105, previously `CONFLICTING`, is now `CLEAN`/`MERGEABLE`** as a direct side effect, since it was hitting the same underlying divergence. The live checkout's own local branch was deliberately NOT touched (still behind origin's now-updated version) — it will catch up naturally on its own next pull; force-syncing a shared, actively-committed-to local checkout was out of scope and unnecessarily risky for what this fix needed.

**Lesson for next time:** "predates PR #N, so it's local-only" needs a `git merge-base --is-ancestor <commit> origin/<branch>` check before asserting reach — the same class of mistake as the `522075e` correction below, caught twice in one session. And "git reports a clean merge" is not the same claim as "the merge is semantically correct" for structured config files — a JSON-aware duplicate scan is required whenever two branches independently insert into the same array, even with zero conflict markers.
