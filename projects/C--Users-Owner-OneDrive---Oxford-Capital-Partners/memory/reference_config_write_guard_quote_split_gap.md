`hooks/config-write-guard.py`'s shell-command matcher (`classify_shell`, `hooks/lib/tool_call_paths.py`'s `shell_may_write`) resolves a target path by scanning the raw/normalized command TEXT for markers or drive-qualified absolute-path tokens (regex-based, not real argv/shell tokenization). A shell command that splits a governance path across a quoted and immediately-adjacent unquoted fragment defeats this: `cp x.json "<root>"/hooks/evil.py` (or the same trick with `settings.json`, `CLAUDE.md`, `workflows/**`, via Bash or DC start_process/cmd.exe) is NOT classified as a governance/claim hit and passes unblocked, even though POSIX shells and cmd.exe both concatenate the quoted and unquoted runs into one real path at execution time and the write genuinely lands on the live file.

**Confirmed pre-existing, not a regression:** tested directly against `git show main:hooks/config-write-guard.py` (the untouched, never-edited-this-session version) -- the exact same payload returns `classify_shell(...) -> None` there too. A companion `..`-traversal class of bypass (`<root>/nonexistent_dir/../hooks/evil.py`) was ALSO confirmed pre-existing in the original code, but the 2026-07-21 boundary-fix session's redesign (`_shell_absolute_hits` reusing `_norm`/`_classify`'s `os.path.realpath`-based resolution) fixed that specific class as a side effect -- verified as a net improvement, not a tradeoff. The quote-split class remains open; no fix was attempted for it in that session (see [[project_config_write_guard_boundary_fix_2026-07-21]] for full session history).

**Why not fixed inline:** the module's own docstring explicitly says "do NOT narrow" the shell-command matcher, citing [[feedback_autonomy_gate_matcher_cannot_be_safely_narrowed]] (3 prior narrowing rounds on the sibling `ora-autonomy-gate.py` each reopened a bypass). Robustly closing the quote-split class requires real shell-argument tokenization (proper quote/escape-aware argv splitting), not another regex tweak -- a materially larger undertaking than a text-matcher patch, and exactly the kind of change that doctrine says needs its own dedicated, carefully-reviewed session rather than a reactive patch.

**How to apply:** if scoping a future hardening pass on config-write-guard.py / ora-autonomy-gate.py, treat "quote/unquote path-splitting" as a known open attack class alongside value indirection (variables, concatenation) -- both are already-documented "structural ceilings" of pure text-matching. Any fix attempt needs its own adversarial REFUTE pass before landing (mandatory per Engineering OS for hooks/** security-gate code) -- see [[feedback_refute_pass_proactive_default]].

**Companion gap found in the same session's REFUTE round 3, also confirmed pre-existing:** cmd.exe caret-escaping. `cmd /c copy /y x.json <root>/cla^ude.md` (or `settings^.json`, `ho^oks/evil.py`) -- cmd.exe silently strips an unescaped `^` before the invoked program ever sees the argument, so the real write lands on `CLAUDE.md`/`hooks/evil.py`, but the guard's text-matcher sees the literal (caret-containing) string, which matches no marker and produces no absolute-path-token hit either. Verified identically against `git show`'s untouched original -- same pre-existing class as quote-splitting (shell/interpreter-level character processing the text matcher can't see through), not a regression. Left open for the same reason: needs real cmd.exe-aware tokenization, not a regex patch.

**Fixed in the same session (NOT part of this open gap):** a related-looking but actually-closable issue -- Win32's `CreateFile` silently strips trailing `.`/` ` from a path's final component (`CLAUDE.md.` == `CLAUDE.md` on disk), which `os.path.realpath()` does not replicate. This one WAS fixed (in `_norm()`, stripping trailing `.`/` ` from the final path component before comparison) because unlike quote-splitting/caret-escaping it doesn't require shell tokenization -- it's a static, well-defined Win32 path-canonicalization rule, safe to encode directly. It was also confirmed to predate this session (bypassed the live, untouched hook for a plain structured `Write` call), but was in scope to fix here since the fix is simple, mechanical, and shared by every `_norm()` caller (structured file-tool paths AND shell-text absolute tokens) rather than reactive matcher-narrowing.
