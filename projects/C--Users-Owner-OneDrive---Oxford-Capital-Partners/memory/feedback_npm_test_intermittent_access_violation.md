**Correction (2026-07-08, same day): my first pass at this was wrong.** I initially concluded this was a Git-Bash/MSYS2-only reporting artifact after 3/3 clean runs via `cmd.exe` — too few samples for a genuinely intermittent failure. Re-tested more thoroughly: the exact same crash (exit code `-1073741819` = `0xC0000005` = `STATUS_ACCESS_VIOLATION`) reproduces via Git Bash, PowerShell/`cmd.exe`, AND a direct `node node_modules/vitest/vitest.mjs run` invocation with npm's wrapper fully bypassed. It is not shell-specific.

**What's confirmed:**
- 100% of actual test assertions pass in every single run, right up until the crash — never any content correlation.
- Crash location is non-deterministic — different test files each time (sometimes mid-suite, sometimes the very last test), ruling out any single test/file as the trigger.
- `vitest.config.ts` already pins `pool: 'threads', singleThread: true` for a different, previously-diagnosed Node24+Windows `forks`-pool spawn fault — this is a further symptom of the same general Node24+Windows+native-module (better-sqlite3/sharp/onnxruntime, all loaded somewhere in the ~2330-test suite) fragility, not a new category of bug.
- **No Windows Error Reporting Application-Error event** is logged for any of these crashes (`Get-WinEvent -LogName Application`), despite `WerSvc` running normally with no disable flag set.
- **No crash dump is produced** even after explicitly configuring per-user `HKCU:\...\Windows Error Reporting\LocalDumps\node.exe` (DumpType=2/full, confirmed the registry key took). A genuine unhandled SEH exception inside node.exe WOULD produce a dump here.

**Working conclusion:** the access-violation exit code is very likely being set by something TERMINATING node.exe from outside (e.g. `TerminateProcess` with that status code) rather than an actual unhandled exception inside the process — external termination bypasses WER's unhandled-exception pipeline entirely, which is consistent with zero WER events AND zero dumps despite a "crash-shaped" exit code. Strongest remaining suspect (not confirmable without admin rights on this machine): antivirus/EDR real-time protection reacting to the rapid loading of several native `.node`/DLL modules during a fast, single-threaded, ~2330-test run. Ruled out: any specific test file, the codebase itself, vitest config content, and the invoking shell (Git Bash vs. cmd vs. direct node — identical behavior in all three).

**Correlation spotted on a later round (6 consecutive crashes, same session):** 4 of 6 clustered right around `tests/unit/capital-allocation-api.test.ts`'s R-1 test — which calls `mkdtempSync` + `openWarehouse` (a fresh better-sqlite3 `.sqlite` file written to a brand-new temp dir) and is the single slowest test in that neighborhood (2-2.7s). This is exactly the shape of operation real-time AV scanning reacts to (new file write from a native addon in a temp dir) — consistent with, not a reversal of, the AV/EDR working theory above. Not proof (dozens of other tests do similar `openWarehouse`-on-tempdir operations without incident, and crash location was NOT this test in earlier rounds of the same investigation), and still not confirmable without admin rights to inspect Defender/EDR logs directly — but if this recurs, that test's setup pattern is the first place to look.

**How to apply:** if `npm run test`/`gate` (in any shell) exits with a Segmentation-fault-style message or code `-1073741819`/`0xC0000005`, do not treat it as a codebase or vitest-config bug — the content is correct. Just rerun; a clean run happened within 1-3 attempts earlier in this same investigation, though a later round needed 6+ (crash frequency is not stable/predictable — treat "just rerun" as probabilistic, not guaranteed-fast). Do not sink further time re-diagnosing this without admin access to actually inspect AV/EDR logs (Defender's own detection history was checked and was empty, but exclusions/heuristic actions aren't visible without elevation). Confirmed again 2026-07-08 in a separate PR #185 session (3 consecutive gate crashes, 3rd attempt clean, 2337/2337 tests) — same signature, same "just rerun" resolution. See [[oxford-command-center-worktree-gotchas]] for a related but distinct EPERM (not access-violation) failure mode in the same family, specific to running `warehouse:verify` from inside a worktree.
