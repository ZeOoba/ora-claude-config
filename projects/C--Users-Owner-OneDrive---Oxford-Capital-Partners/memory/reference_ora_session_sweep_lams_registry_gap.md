On 2026-08-11 `ora-session-sweep` (a LAMS/Cowork-fleet task per its own SKILL.md header) executed in what was actually a Code-surface session. Its Step 1a call to `list_scheduled_tasks` returned only the CC/MCP registry (~29 tasks under `~\.claude\scheduled-tasks\`) — it did not list `ora-session-sweep` itself, which is LAMS-registered. Net effect: Step 4a's title-to-task matching (for sourcing a session's `date:` frontmatter) could not resolve titles belonging to LAMS-only tasks, e.g. "Health Guard FAIL-Aging follow-up" (→ `ora-health-guard-fail-aging-nudge`, LAMS-side per the active-context roster). Those sessions fell back to index-date instead of a sourced date.

**Open question, not yet resolved:** is this a genuine capability gap (`list_scheduled_tasks` is architecturally single-fleet no matter which surface calls it), or just a surface-dispatch mismatch (this specific run got CC/MCP-scoped tools despite the task being LAMS-owned, and a genuine LAMS-surface run would see the LAMS registry fine)? Not testable from Code — needs a supervised Cowork/LAMS session to call `list_scheduled_tasks` and check whether LAMS-only tasks (e.g. `ora-session-sweep` itself, `ora-health-guard-fail-aging-nudge`) appear.

**Why this couldn't just be fixed in place:** [[reference_tech]]'s register-scheduled-task doctrine Rule 1 — register/update a task's SKILL.md content only via `create_scheduled_task`/`update_scheduled_task`, from a supervised session, **on the surface where the task runs**. This session (Code) can't reach a LAMS-scoped `update_scheduled_task`, and improvising a raw filesystem edit to the LAMS SKILL.md store is exactly what Rule 1 says not to do.

**Resolution path (Gabriel's call, 2026-08-11):** hand off to a Cowork session rather than edit from here or accept the gap as-is. See [[open-items-tracker]] OI-121 for the live tracking row — do not restate its text here, it will drift.

**If Cowork's `list_scheduled_tasks` DOES see the LAMS registry:** this whole finding downgrades to "surface mismatch in one run," not a standing defect — no SKILL.md change needed, just close OI-121 with that evidence.

**If it doesn't:** the fix is a Step 1a fallback in `ora-session-sweep`'s SKILL.md that reads both registry JSONs directly via filesystem (LAMS: `...Documents\Claude\Scheduled\`; CC/MCP: `~\.claude\scheduled-tasks\`) for cross-fleet title matching, applied via `update_scheduled_task` per Rule 1, then re-verified with `list_scheduled_tasks`.

**2026-08-12 follow-up — checked the fleet-status/fleet-contract producer chain for the same class of bug; it's clean, and it points at the actual fix shape.** Traced `fleet-status.py`, `fleet-contract-check.py`, `registry-membership-probe.py`, and `emit-fleet-heartbeat.py`: all four discover tasks via direct filesystem reads of BOTH registry JSONs through `maintenance/_shared/store_discovery.py` (globbing `claude-code-sessions` and `local-agent-mode-sessions` stores), never through the surface-scoped `list_scheduled_tasks` MCP tool — so none of them share this bug. `fleet-contract-check.py` doesn't even touch scheduled-task registries directly; it just checks `_state/*.json` mtimes, which is surface-agnostic by construction.

Better still: `fleet-deadman.ps1`'s own alert text already documents the exact CC/MCP-only limitation of the raw tool — *"Re-check inside Claude: `list_scheduled_tasks` (cc fleet) or `maintenance\fleet-status.py` (both)."* — so this isn't an unknown gap, it's an established one with an established workaround the fleet tooling already uses. **Revised fix recommendation for OI-121 (if the Cowork-side check confirms a real gap, not just a surface mismatch):** point `ora-session-sweep` Step 1a at `fleet-status.py --json` (or replicate the `store_discovery.py` pattern directly) instead of calling `list_scheduled_tasks`, mirroring the pattern every other dual-fleet-aware script in `maintenance/` already uses — not new dual-registry-read logic from scratch. Caveat: `fleet-status.py --json`'s `tasks[]` array does not currently expose `lastRunAt` per task (only `id`/`fleet`/`enabled`/`cron` — confirmed by reading `main()`'s JSON block), even though the underlying registry JSON has it and the human-readable table prints it. Either extend the JSON output with `lastRunAt`, or read the registry file paths `fleet-status.py` already prints (`registry[cc]: <path>`, `registry[lams]: <path>`) directly for that field.
