Never follow a pathspec-scoped `git commit -m "..." -- <file>` with a same-file surgical splice already staged via `hash-object` + `update-index --cacheinfo`. The pathspec form re-reads the **working tree** for that path at commit time regardless of what the index holds — it silently discards the splice and commits the raw working-tree file instead, re-sweeping in whatever a co-mingled writer left there.

**Why:** confirmed by a real incident 2026-07-22. [[reference_commit_provenance_guard]] correctly blocked a commit because another live session (`40a4b051`, SEO-audit work) had touched the same MEMORY.md within TTL. Once that session ended, I re-staged just my one-line fix via `hash-object` + `update-index --cacheinfo` — the exact [[reference-event-log-partial-commit-splice]] technique — and verified `git diff --cached` showed only my line. But I then ran `git commit -m "..." -- MEMORY.md`, which is the guard's own suggested remediation text ("commit only your own files with an explicit pathspec"). That pathspec form ignored the surgical index and committed the full working-tree file, landing four unrelated hunks from the other session's SEO-audit work under my commit message (`61facf4`). Caught by re-reading the diff after commit, not before — the guard has no post-commit check. Fixed by amending the message to accurately describe all five changes (`62e5a35`) rather than reverting, since the swept-in content was itself complete, correct, finished work — reverting would have destroyed it.

**How to apply:** after any `update-index --cacheinfo` splice, the closing commit must be a **bare `git commit -m "..."` with no pathspec at all** — unstage any other paths first (`git reset -- <other-path>`) if the index has anything else in it. **Prefer the temp-index variant when that "anything else" belongs to another live session** (added 2026-08-12): unstaging their paths preserves their file content but destroys their staging selection, which is still a disruption you don't have to inflict. Seed a scratch `GIT_INDEX_FILE` from HEAD, stage only your own content into it, and commit from there — `.git/index` is never written, so their staged set survives untouched. Full recipe, including the staged-revert repair that step leaves behind, in [[reference_event_log_uncommitted_backlog]]. A pathspec is only safe when the named file's working tree already equals exactly what you intend to commit (i.e., no splice involved). Both [[reference-event-log-partial-commit-splice]] step 6 and the guard's own block-time remediation text in `hooks/commit-provenance-guard.py` now carry this caveat inline, so future sessions following either shouldn't hit this blind.

**RECURRED 2026-08-05, independently, on a different file — the `--only` form is the SAME failure mode, not a safer alternative.** A session isolating edits to `open-items-tracker.md` (concurrently mid-edit by other live sessions with a ~600-line unrelated addition too close in the file to hunk-split) built and verified a clean splice via the exact technique above, then closed with `git commit --only -F <msg> -- <path>`. `--only`/`-o` was chosen believing it meant "commit only what's staged for this pathspec" — it does not. Per git's actual semantics, `--only` with an explicit pathspec re-reads the **working tree** for that path, identically to the bare pathspec form this file already warns about — the flag name is misleading, not a distinct safer mode. The splice was silently discarded and the commit absorbed everyone's concurrent edits, including unreviewed HIGH/CRITICAL security findings from another session, under a message describing only 3 items. No data was lost (the content itself was legitimate, real work — just misattributed), and it was caught immediately by diffing the resulting commit, but the fix was a same-day event_log correction rather than a rewrite, since by the time it was caught the commit was already pushed. **Extend the rule above: no pathspec at all, in ANY form — not `-- <path>`, not `--only <path>`, not `--only -- <path>` — may follow an `update-index --cacheinfo` splice.**

**Root cause of the recurrence, worth naming:** this exact gotcha was already fully documented here and in [[reference-event-log-partial-commit-splice]] before 2026-08-05 — the session that hit it again did not consult either file first, despite [[INDEX_reference]] existing precisely to catch this ("open it before debugging any tooling failure or assuming a gotcha is unrecorded"). See [[feedback_verify_freshness_before_acting]] for the broader lesson this instance is one symptom of.
