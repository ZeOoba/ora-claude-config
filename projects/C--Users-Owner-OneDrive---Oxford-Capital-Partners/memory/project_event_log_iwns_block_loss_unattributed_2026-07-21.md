**What happened:** 6 contiguous entries (IWNS LLC lease verification, OI-023 closure, rent-roll reconciliation spinoff, 60-row portfolio-wide reconciliation, I Dig Ditches, Childs Play Diesel Performance) — all safely committed by session `15ec64e8` between 2026-07-20 18:47 and 23:32 EDT via the isolated-hunk `git apply --cached` technique ([[reference_event_log_uncommitted_backlog]]) — were absent from the working-tree copy of `event_log.md` by the time a later session (this one) read the file at 2026-07-21T16:21Z. Not archived, not rolled over — just gone from disk while everything else (older AND newer entries) stayed intact. Content fully recovered verbatim from `git show HEAD` and committed at `0d63e25`. This memory records the root-cause investigation, which came up empty despite real effort — so a future session doesn't re-walk the same dead ends.

**Ruled out, with evidence:**
- `append-event-log.py` race/in-place-fallback bug — zero invocations of this script (any fleet) found anywhere in the 2026-07-21T03:32–16:05Z candidate window. Its `_inplace_insert()` mtime-guard was also already hardened and validated zero-data-loss on 2026-07-16 ([[reference_event_log_app_handle_lock]]) for a *different* symptom (blocked append, not content loss).
- Any Code-session `Edit`/`Write`/`MultiEdit` targeting `event_log.md` in the window — none found (full transcript scan, all 382 project `.jsonl` files).
- Any LAMS/Cowork `write_file` targeting the canonical path in the window — none found (full scan, ~475 LAMS transcripts). The only in-window LAMS writes to the file were: (1) session `15ec64e8`'s own commit of the IWNS block itself (the write that *added* the content), and (2) a legitimate `edit_block` append at 16:04:15Z anchored to the bottom rollover divider (unrelated area of the file, added the 2026-07-13 lease-expiration-brief entry) — its `old_string` anchor already showed the IWNS block missing, meaning the loss predates 16:04:15Z but that call didn't cause it.
- The shared-checkout-guard's attribution of session `a039bb1f` — independently confirmed false; see [[feedback_shared_checkout_guard_session_attribution_unreliable]] (third instance, its own transcript never touches event_log.md at all).

**Net: exhaustive search across every tool-call type (Edit/Write/MultiEdit/Bash/edit_block/write_file) on both fleets, in the only window the loss could have occurred, found no write event capable of explaining it.** The mechanism is NOT any previously-documented failure mode for this file.

**Leading hypotheses, unconfirmed:**
1. A Cowork/LAMS-internal file-cache or checkpoint mechanism that writes back a stale buffer outside the visible `mcp__Desktop_Commander__*` tool-call audit trail entirely (i.e., a write path this investigation has no visibility into).
2. Some variant of the Claude.exe held-handle behavior ([[reference_event_log_app_handle_lock]]) beyond what's documented there — that reference only describes a *read* handle blocking `os.replace`, not a write. If the app itself ever writes back a tailed/cached copy of a memory file it's watching (plausible given the "file was modified" live-tail behavior noted in that doc), that would explain a silent, tool-call-invisible content loss.

**How to apply:** if this recurs, capture evidence fast — the git-history recovery here only worked because 15ec64e8's commits landed before the loss. Check `git diff HEAD -- event_log.md` for unexplained removals (not just the usual insertions) before committing any backlog blindly; this is why [[reference_event_log_uncommitted_backlog]]'s "isolate and verify" discipline caught it. If it happens again, immediately check whether Claude.exe (Desktop app) was running/idle at the estimated loss time and whether Restart Manager shows it holding a handle — that's the one lead worth chasing further, and wasn't checked live here since the loss was discovered hours after the fact.

**Live confirmation, same session, ~30 min after filing this:** ran the Restart Manager check (RmStartSession/RmRegisterResources/RmGetList via PowerShell Add-Type, same technique as [[reference_event_log_app_handle_lock]]) against the live file. Result: **2 Claude.exe processes currently hold it open** — pid 26948 (started 11:58:04 ET) and pid 20204 (started 12:38:02 ET), both `Type=0, Restartable=False`. Process-tree lookup (`Get-CimInstance Win32_Process`) showed both are `--type=utility --utility-sub-type=node.mojom.NodeService` children of the single main app process (pid 4616) — headless Node service workers, NOT visible GUI windows (neither had a `MainWindowTitle`). pid 26948 was one of 8 near-simultaneous utility workers spawned in the app's 11:58:03–11:58:11 startup burst (generic pool); pid 20204 was spawned alone, much later, standing out from that pattern.

**Controlled test (same session):** snapshotted the file (SHA256 `d8c53991...`, 150448 bytes, mtime 12:44:47.046) immediately before gracefully stopping pid 26948 (`Stop-Process`, not force-kill). Process exited cleanly within 3s; Restart Manager re-check confirmed holder count dropped 2→1 (only pid 20204 remained). Re-hashed the file: **identical** — same SHA256, same size, same mtime, zero bytes changed. Releasing this handle triggered no write-back whatsoever.

**Revised conclusion:** this is real evidence AGAINST the "app flushes a stale cached buffer on handle-release" theory, at least for this utility-process handle type — it does NOT establish that holding the handle is causally connected to writing anything. The mechanism behind the original IWNS-block loss remains genuinely unexplained; holding a handle open (confirmed, routine, benign in this test) is not the same as writing stale content (never observed, in this test or the transcript search). Don't over-read the earlier "2 holders" finding as progress toward a cause — it's currently a dead end. If this recurs, the more promising angle would be to catch a write in progress (e.g., a file-system watcher / auditing tool armed ahead of time), not handle-holder identity, since holding ≠ writing per this test.

**Second controlled test, same session, immediately after:** repeated the identical before/close/after procedure on the remaining holder, pid 20204 (`Stop-Process`, graceful, exited within 3s). Same snapshot hash (`d8c53991...`, 150448 bytes, mtime 12:44:47.046) confirmed unchanged since the first test — no intervening write from anything else. Restart Manager now reports **0 holders** on the file entirely. Post-close hash/size/mtime: identical again, zero bytes changed. Both live handles this session are now cleared and BOTH produced a clean null result — this wasn't a fluke of picking the "safer" one; the theory fails symmetrically for both. Hypothesis #2 (app-handle-release write-back) is now considered closed/rejected for this file, based on 2/2 controlled tests. The loss mechanism is back to fully unknown — no live leads remain from this angle. Any future recurrence needs to be caught in the act (a filesystem write-auditing tool armed in advance), not reasoned about after the fact from handle state.
