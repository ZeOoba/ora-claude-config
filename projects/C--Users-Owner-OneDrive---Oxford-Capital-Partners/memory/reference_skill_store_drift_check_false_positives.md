**The finding.** The 2026-08-03 `ora-skill-store-drift-check` reported 12 skills CACHE-NEWER and prescribed a byte-exact cache→repo pull for all 12. Verification against disk before any write invalidated 10 of them:

- **9 were already EOL-normalized IN-SYNC**, and **7 of those were byte-identical** to the cache. No content comparison could produce those flags — the check is reading stale **version tokens** (frontmatter/index descriptions, changelog dates), not file content.
- `market-monitor` and `tenant-email` differed **only in CRLF** — the known false-positive class, which the check also does not normalize away.
- `acquisition-underwriting` was reported as cache v4.6 / 138,460B. Actual cache state was **v4.7 / 146,847B** — the cache had advanced again *after* the check ran. **Its byte-size and version figures are point-in-time and rot fast** (see [feedback_prompt_current_state_prose.md](feedback_prompt_current_state_prose.md)).

**Why this matters more than a nuisance.** Of the 3 genuinely-drifted skills, **none** could take the prescribed byte-exact copy — all tripped a gate in the recovery procedure. Two tripped the step-3 anomaly gate (**neither side a superset**): the cache body was newer but the cache *frontmatter description* was a regression. `parcel-data-recovery`'s cache description had collapsed **850 → 203 chars, losing every trigger phrase** (`recover SF`, `UNSCREENABLE rows`, `DATA-GAP rows`, `CAMA extract`, `county GIS pull`, the verified-endpoint county roster). **A byte-exact copy as instructed would have silently destroyed that skill's entire routing surface.** `disposition-analysis` showed the same regression more mildly (lost Sec 1245 / unrecaptured Sec 1250 / NIIT / 45-180-day / QI-boot / estate-step-up detail).

**MERGED to `main` 2026-08-03 at `370c4d8`** — PRs [#31](https://github.com/ZeOoba/ora-skills/pull/31) + [#32](https://github.com/ZeOoba/ora-skills/pull/32) + [#33](https://github.com/ZeOoba/ora-skills/pull/33), verified on main (168 tests) and run live via the SKILL.md's hardcoded path. ⚠️ The merge did NOT make it live by itself: the task invokes `C:\Users\Owner\ora-skills\tools\...`, i.e. the **local main checkout**, which had to be fast-forwarded separately — a merged PR is not a deployed tool here. **CACHE-ONLY trio RESOLVED** ([PR #34](https://github.com/ZeOoba/ora-skills/pull/34)): `lease-form-qc` and `masterlease-jurisdiction-rebase` captured into the repo (byte-exact — safe for a capture, unlike a drift pull, since there is no repo copy to overwrite); **`morning` was NOT captured** — zero Oxford/ORA mentions, same profile as stock `schedule`/`setup-cowork`, so it went into `STOCK_SKILLS`. Capturing it would have created a bogus authoritative source for a skill ORA doesn't own, drifting on every platform update. **CACHE-ONLY is a prompt to decide provenance, never an instruction to capture.** Note: capturing a cache-only skill always leaves FALSE PENDING_REIMPORT entries (the cache already matches, since the content came from it) — verify `skill_drifted == False` and clear them in the same session.

**FIXED 2026-08-03 — drift-check v1.12 ([PR #31](https://github.com/ZeOoba/ora-skills/pull/31)).** Step 2's verdict no longer lives in prose for the model to execute by eye; it is delegated to `tools/skill_drift_report.py`, which does all four steps below mechanically: EOL-normalized SHA256 both sides (NUL padding stripped), frontmatter vs body compared **separately** as distinct findings, direction from **per-part git ancestry** rather than version markers, and a new **MANUAL-MERGE** verdict that refuses the byte-exact pull whenever neither side is a superset. The byte-exact CACHE→REPO recovery procedure is now gated on a `CACHE-NEWER` verdict, which only issues when every differing part is a clean cache-side superset. Version/byte figures are quarantined under a `read_at`-stamped `point_in_time` key and rendered "NOT authoritative"; the cache is re-hashed at end of run and flagged `CHANGED-DURING-RUN` if it moved. 37 stdlib tests, one per false-positive class above. Live re-run, stamped with the repo revision measured against: **vs repo @189bd28, 19:39Z → 41 IN-SYNC, 3 MANUAL-MERGE, 10 NOT-INSTALLED** (12-flag cluster gone; the 3 survivors exactly the manually-confirmed ones); **vs repo @e0aba43, 19:48Z → 44 IN-SYNC, 0 drifted** — the remediation PRs for those 3 merged in between. Both correct at their revision; quoting either bare is the same rot this fix removes. **Both original caveats closed by [PR #32](https://github.com/ZeOoba/ora-skills/pull/32)** (real-data coverage, stacked on #31), which found a real defect behind each: (i) three live skills (`census-acs-extract`, `ratify-hurdle-rate`, `oxford-cc-strategic-audit`) declare `description:` as a **YAML folded block scalar**, and the old regex returned literally `'>'` for all three — so `len(cache) < len(repo)` could never fire and **the regression detector was silently dead on them**; `description_of` now folds block scalars and strips quotes (parcel-data-recovery reads 850, matching this record, not 852), with a conformance sweep over every real SKILL.md. (ii) the reorder rule was only half true — `_line_subset` used an order-blind `Counter`, so a cache that **reordered AND appended** read as a clean superset → CACHE-NEWER → byte-exact pull, silently imposing the platform's section ordering on the repo; it is now an **ordered-subsequence** test, and the CACHE-NEWER remedy no longer overstates itself (content + ordering verified, blank-line/whitespace structure explicitly NOT). Blank lines stay ignored on purpose so whitespace churn can't manufacture a MANUAL-MERGE.

**Critical review finding — FIXED on the #31 branch (commit `5b017a6`).** `_part_history_hashes` returned an *empty set* (not `None`) when `git rev-list HEAD -- <path>` exits 0 with no output, so `classify_shared_copy` skipped UNKNOWN and returned **CACHE-AHEAD** — shipping the destructive pull on no evidence. Inferred-null masquerading as verified-null (cf. [feedback_verified_null_vs_inferred_null.md](feedback_verified_null_vs_inferred_null.md)). Two reproduced triggers: an **untracked** SKILL.md reported CACHE-NEWER; and in a **shallow clone** a section the repo had deliberately DELETED read as cache-side-new, so the pull would have re-introduced it. The shallow case needed its own guard (`rev-parse --is-shallow-repository`) — the empty-set check does not catch it, since rev-list returns a revision, just not the relevant one. Same fix applied to `pending_reimport._file_history_hashes`.

⚠️ **An existing test CERTIFIED that defect** — `test_file_history_hashes_none_none_when_file_never_committed` was named for `(None, None)` but asserted `set()`, with a comment reasoning that a successful-but-empty `rev-list` "must not be conflated with git-unavailable". True at the git layer, wrong at the consumer: `classify_shared_copy` treats any non-`None` set as a completed search. That is why the bug survived review. Reversed, with the reasoning recorded in the test. **Residual, undetectable:** if cache content was committed only on a branch later deleted or gc'd, ancestry genuinely loses it and DIVERGENT decays to CACHE-AHEAD — so the safety net erodes over time with `clean_gone`; the MANUAL-MERGE superset gate is the backstop. **YAML quoting FIXED as a class** ([PR #35](https://github.com/ZeOoba/ora-skills/pull/35)): `acquisition-underwriting`'s recurring MANUAL-MERGE was repo `name: "x"` vs cache `name: x`. A one-character file fix would have recurred — the QUOTED form was itself pulled *from the cache* by the 2026-07-27 REPO-FIRST recovery (`20a936e`), and the same cache later served it unquoted. **The platform re-serializes frontmatter on install and its quoting style varies over time**, so `_normalize_frontmatter` now gives a compare-only, quoting-insensitive view (top-level scalars only; block scalars untouched). ⚠️ **Unquoting a YAML scalar discards the leading/trailing whitespace quotes exist to protect** — feeding that view into the *reporting* path shaved a char off a described length (203→202, caught by the replayed real-data fixture). A compare-only normalization must never reach a reported figure.

**YAML quoting fix was NOT repo-wide — a second, separate comparator had the same gap, FIXED 2026-08-04** ([PR #38](https://github.com/ZeOoba/ora-skills/pull/38)): `_normalize_frontmatter` lived in `skill_drift_report.py` only. `pending_reimport.py` has its OWN whole-file hash comparator (`_normalized_hash_bytes`, feeding `skill_drifted()`/`sweep_drift()`/`candidates()` — the ledger consumed by `ora-skills-reimport-watch` and `package-and-stage-skill`) and was never updated alongside PR #35. Caught live: a confirmed-correct Save-skill install of `masterlease-jurisdiction-rebase` — content-identical to the repo except for the same quoting-class delta plus a trailing blank line — still read as a `candidates` hit. Fix: extracted `split_skill_md`/`_normalize_frontmatter`/`_unquote` into a new shared `tools/skill_md_normalize.py` (moved verbatim, not reimplemented) that both modules import, plus a `normalize_skill_md_text()` helper (no-op for anything that isn't frontmatter-fenced, so non-SKILL.md bundled files are unaffected) wired into `pending_reimport._normalized_hash_bytes`. **Lesson: a normalization fix in one comparator does not imply the other agrees — this repo has at least two (`skill_drift_report.py`'s part-based compare, `pending_reimport.py`'s whole-file hash) with no shared test asserting they produce the same verdict on the same fixture.** 125 tests green (47+63+15); live-reverified against the real cache before/after.

**Standing procedure before acting on any drift-check report** (now automated by the above — apply by hand only to reports dated **before** 2026-08-03, or when the task reports "UNVERIFIED — comparator unavailable"):
1. Re-hash both sides yourself, **EOL-normalized** (`sha256(bytes.replace(b"\r\n", b"\n"))`). Expect a large share of reported drift to vanish.
2. For anything still drifted, diff **frontmatter and body separately**. Cache-newer body + repo-newer description is a real and recurring pattern — platform-side edits regularly truncate the description, which is the skill's routing surface.
3. Never trust the report's version/byte figures; read the actual version token off disk. The cache is a **live, moving target** — it changed underneath this very session between two verification passes.
4. Merged descriptions must stay **≤1024 chars** (platform import limit; pre-commit Check 2 enforces it).

**Direction of the error is consistently self-flattering to the tool** — it over-reports work to do, and its prescribed remedy is destructive where it is wrong (cf. [feedback_self_flattering_error_bias.md](feedback_self_flattering_error_bias.md)).
