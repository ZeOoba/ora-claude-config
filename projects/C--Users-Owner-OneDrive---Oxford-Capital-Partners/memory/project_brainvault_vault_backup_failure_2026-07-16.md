**Fix mechanism:** `session-capture.ps1` now launches `vault-backup.ps1` via `Start-Process -PassThru` + `.WaitForExit(25000)` instead of fire-and-forget — bounded-synchronous, so the hook process doesn't return (and nothing tears down) until the backup finishes or 25s elapses. A Scheduled-Task-based escape (register a task, trigger via `schtasks /run`) was tried first and rejected: task creation and `/run` both reported success, but a trivial `cmd.exe echo > file` action registered the same way also silently never executed — consistent with a "Log on as a batch job" / empty-password local security-policy restriction on this machine, which is not something to silently work around. The synchronous-wait approach was validated in an isolated scratchpad harness (launcher/worker pair) before being ported into the real scripts, and the modified `vault-backup.ps1` was further validated end-to-end (commit+push+status+log all correct) against a throwaway local repo+bare-origin pair — never against the real BrainVault backlog, to avoid `git add -A` sweeping it up.

Original root-cause investigation, 2026-07-16: `C:\Users\Owner\Obsidian\BrainVault`'s Stop-hook auto-backup chain (`.claude/settings.json` → `.claude/scripts/session-capture.ps1` → detached `vault-backup.ps1`) has committed **zero** backups since `664a0bd "backup: 2026-07-10 20:05"`, despite the Stop hook itself firing reliably (session-mirror `.md` files and daily-note breadcrumbs are being written continuously — 15+ in a single 6-minute window observed live during this investigation). Working-tree backlog grew from 1,113 → 1,123 paths *during* the investigation itself, confirming this is an active, ongoing failure, not a historical one-off gap.

**Root cause (leading hypothesis, strongly evidenced but not yet directly instrumented):** `session-capture.ps1` launches `vault-backup.ps1` via `Start-Process -WindowStyle Hidden` (no `-Wait`) to avoid blocking session end. On Windows, `Start-Process` detaches from the *parent-process* relationship but does **not** break the child out of a Windows Job Object — child processes join their ancestor's job by default unless spawned with `CREATE_BREAKAWAY_FROM_JOB`, which `Start-Process` never sets. If Claude Code's own process is job-object-scoped with kill-on-close semantics (typical for Node CLIs on Windows, to prevent orphans), the "detached" `vault-backup.ps1` gets killed the instant the parent Claude Code process/job tears down at session end — before it can complete `git add`/`commit`/`pull --rebase`/`push`. The one success on 07-10 20:05 landed immediately after a same-day TOCTOU lock-race fix (`ea4852c`), in what was almost certainly a live/attended terminal session that stayed open past the hook's return — long enough for the detached child to survive and finish. Every non-attended session-end since has failed silently.

**Why it's invisible:** `vault-backup.ps1` only writes `.claude/backup-status.json` (single overwritten snapshot, updated **only** on a non-crashing exit path) — it never writes to `.backup-log/`, even though `.gitignore` documents that path as "vault-backup run log (local only, one line per run)". `Write-Host`/`Write-Warning` output from the hidden detached window is discarded (no console attached, no redirection). So a run killed mid-`git push` leaves **zero trace** anywhere — `backup-status.json` just keeps showing the last completed run's stale timestamp forever.
