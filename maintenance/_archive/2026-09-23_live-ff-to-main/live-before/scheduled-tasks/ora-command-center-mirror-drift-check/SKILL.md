ORA Command Center Mirror — Drift & Health Check (CC/MCP fleet)

PURPOSE: this is the alerting layer for the native Windows Scheduled Task "ORA Command Center - Mirror Deploy" (registered via C:\Users\Owner\oxford-command-center\scripts\register-mirror-task.ps1; runs scripts\deploy-mirror.ps1 hourly all day + a guaranteed 06:45 ET trigger). That script originally (PR #192, 2026-07-09) fast-forwarded THIS checkout with `git pull --ff-only` before baking, to fix a silent-stale-deploy incident (local main sat 7 commits behind origin for an unknown period while the hourly job kept redeploying pre-retokenization code with only a fresh data snapshot — "baked Nm ago" reflects data freshness, not code freshness). **That fast-forward was REMOVED on 2026-08-16 and replaced by an ISOLATED BUILD ROOT** (`scripts/lib/deploy-buildroot.ps1`): the deploy still runs `git fetch origin` here, but then hard-resets a sibling git worktree at `C:/Users/Owner/oxford-command-center-deploy-build` to `origin/main` and bakes THERE. The trigger was the mirror-side twin of the original incident — another session left an uncommitted file in this shared checkout, `build:mirror` exited 2, and every hourly run failed identically while the mirror kept serving a stale bake. The script's own comment gives the rationale: fast-forwarding the shared checkout was "both unnecessary (we no longer build from it) and undesirable: it made an unattended job mutate a tree that humans and other sessions are actively working in, and it re-coupled the deploy's success to that tree's cleanliness." **Consequence for THIS check, and the single most important thing on this page: nothing visible in `git status` on the shared checkout can affect the deploy.** Stated precisely, because the loose version of this sentence is wrong: no `merge`, `pull`, `reset` or `checkout` ever runs against this tree — its only git operations are `git fetch origin`, a `git rev-parse --short HEAD` for the beacon, and a one-time `git worktree add` that creates the build root — so branch position and tracked-file dirt are inert. Both are gitignored, so neither can ever appear in `git status --short` — which is exactly why step 3's reporting-only rule is safe, and why "the shared checkout is irrelevant" is the wrong summary. It is a source of git objects AND machine state. Beware FOUR STALE COMMENTS in `deploy-mirror.ps1` describing the removed fast-forward: the `.DESCRIPTION` header at ~line 20 ("Step 1 below now fast-forwards to origin/main first" — the first thing a reader sees, and the most misleading), ~line 156 ("the pre-fast-forward sha"), the block at ~163-166 above the fetch, and ~204-211 BELOW it (calling `git merge --ff-only origin/main` "the actual command").
