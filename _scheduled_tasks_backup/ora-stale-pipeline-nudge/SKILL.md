ORA Stale Pipeline Nudge — v1.0 (2026-07-08). This is a standing weekly check, intentionally separate from ora-am-brief (Daily Brief) — it exists because 470 McCormick Blvd's blown LOI expiration sat unactioned for 21+ days despite repeated Daily Brief flags, and a distinct weekly nudge with its own subject line is less easy to habituate past.

STEP 1 — Query the source of record. Use the Notion MCP (notion-fetch on the Acquisition Pipeline Tracker database, collection id `collection://bcfe4a03-7e61-4ac1-a0bb-c44174fa138b`) and notion-query-data-sources (SQL mode) to pull ALL rows. Do not guess field names — read the schema returned by fetch first. Never fabricate a deal, stage, or date that isn't actually in the row.

STEP 2 — Filter for staleness. A deal qualifies for the nudge if ALL of:
  (a) `Last Updated` (or equivalent last-modified property) is more than 14 days before today,
  (b) `Target Close Date` is empty/null,
  (c) `Stage` is NOT in (Passed, Closed, Killed, Dead) — treat any stage name that clearly means the deal is inactive the same way,
  (d) the row is NOT explicitly PARKED — its `Next Action` or `Notes` does not begin with / clearly carry a `PARKED` or `ON HOLD` marker. A deal deliberately parked with `Stage` kept `Candidate` (e.g. **Liberty Office Park** — parked 2026-07-09 pending the Cincinnati-cluster decision) is a MADE disposition, not a missing one; do not nudge it. If a parked marker lacks a revisit date, note that once and move on — do not re-flag weekly.
Compute exact days-stale for each qualifying row.

STEP 2b — Status-conflict escalation (deal-inactivation gap, added 2026-07-09). The filter above correctly EXCLUDES deals whose `Stage` is already inactive (Passed/Closed/Killed/Dead) — but ORA currently has NO task that WRITES an inactive `Stage` when a deal is decided to pass/close (`ora-passed-deal-tracker` only logs trades of already-passed deals for calibration; it does not flip Stage). So a decided deal can keep a live `Stage` (e.g. "Candidate") and re-qualify as stale every week. Root case: **Liberty Office Park** re-surfaces weekly at `Stage: Candidate` while a 754/Cincinnati-cluster note states it closed/was declined 6/11. Therefore: for any qualifying deal whose `Notes` / `Next Action` / linked-task text clearly states it was passed, killed, closed, or declined at a gate, do NOT silently re-nudge it — list it in a separate **"STATUS CONFLICT — needs a one-field Stage update"** sub-section with the exact conflicting text and the recommended new `Stage`, so Gabriel can flip it once and it drops out permanently. NEVER change the `Stage` yourself (read-only on the pipeline); surface the conflict for the human write. This makes the nudge the detector for the missing auto-inactivation step until a decision→`Stage` writer exists.

STEP 3 — If zero deals qualify: post one line to the Notion Ops Hub (page id `32b6ecd8-9e59-81f2-b329-df3fd0e25062` or its designated automation-log child — search for the current log location if the parent page ID has moved) confirming a clean pass. Do NOT send an email — this task should be silent on a clean week to avoid alert fatigue eroding the daily brief pattern that already failed once.

STEP 4 — If one or more deals qualify: compose a plain, short email. Subject: "[ORA] Stale Pipeline Nudge — {today's date} — N deal(s) need a Target Close Date or disposition decision". Body: for each qualifying deal, list Deal Name, Address, Stage, LOI Status if present, days stale, Broker/Source, and the current `Next Action` field verbatim (do not paraphrase it — Next Action fields often carry load-bearing detail like ship instructions). Do not recommend a specific disposition (re-issue/extend/abandon) unless the deal's own Notes field already states a recommendation — surface the facts, let Gabriel decide.

STEP 5 — Delivery surface (read carefully — corrected 2026-07-09). This task runs on the LAMS/Cowork fleet, which has NO reach to the Outlook COM send path: `send-via-outlook.ps1` is a Windows-local script only callable from a Claude Code / Desktop Commander surface, and no Outlook-send MCP tool is connected on Cowork. There is therefore no COM send to "fail" here — do NOT frame a missing email as a send-path outage or an RPC_E_CALL_REJECTED bug (that earlier framing was inaccurate; it conflated "no COM on this surface" with "COM failing"). Accordingly, the Notion Ops Hub post (STEP 6) is this task's PRIMARY, canonical delivery. Only if this task is ever run from a COM-capable surface may it ADDITIONALLY send via `send-via-outlook.ps1 -To ggoldberg@oxfordra.net` (ONLY — no cc; the Daily Brief cc-Eric exception does not apply here) `-Subject "..." -BodyFile <path> -BodyFormat html`; a non-zero exit there is not this task's bug because the Notion post already carries the full information. Continuity note: the daily `ora-pm-ledger` EOD Action Ledger independently re-surfaces the same stale-deal list to ggoldberg@ via the working COM path each evening, so these deals reach Gabriel's inbox regardless of this task's surface — this nudge's job is the durable, de-habituated weekly record, not the email itself.

STEP 6 — Notion Ops Hub post (PRIMARY delivery, not merely an audit trail). Post the finding — the clean-pass one-liner (STEP 3) or the FULL qualifying-deal list per STEP 4 — to the Notion Ops Hub (`32b6ecd8-9e59-81f2-b329-df3fd0e25062`, or its current automation-log child if the parent page ID has moved). This is the canonical record and the primary channel by which the nudge reaches Gabriel.

Data-gap handling: if the Acquisition Pipeline Tracker schema doesn't have a recognizable `Target Close Date` or `Last Updated` property under any reasonable name, first check FIELD-NAME RATIFICATIONS below for a Gabriel-confirmed mapping for the schema state you're seeing. If it matches a ratified mapping, use that mapping and proceed with STEP 2 normally — note in the Ops Hub post that this run used a ratified field-name override, not a fresh discovery. If it does NOT match any ratified mapping (a genuinely new/different schema state), do not guess — stop, and instead of running the filter, post a "QUESTIONS FOR GABRIEL" flag to the Ops Hub describing exactly which property you expected and what you found instead.
