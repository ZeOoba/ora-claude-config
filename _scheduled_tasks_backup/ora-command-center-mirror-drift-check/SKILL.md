ORA Command Center Mirror — Drift & Health Check (CC/MCP fleet)

PURPOSE: this is the alerting layer for the native Windows Scheduled Task "ORA Command Center - Mirror Deploy" (registered via C:\Users\Owner\oxford-command-center\scripts\register-mirror-task.ps1; runs scripts\deploy-mirror.ps1 hourly all day + a guaranteed 06:45 ET trigger). That script was patched 2026-07-09 via PR #192 ("fix(deploy): mirror deploy fast-forwards to origin/main before baking") to `git fetch origin` + `git pull --ff-only` before baking, and now `throw`s/aborts the deploy on a diverged-or-dirty tree instead of silently redeploying stale code (the original incident: local main sat 7 commits behind origin for an unknown period while the hourly job kept redeploying pre-retokenization code with only a fresh data snapshot — "baked Nm ago" reflects data freshness, not code freshness). PR #192 fixed the silent-stale-deploy failure mode, but added no alerting of its own, and the task itself lives entirely OUTSIDE this MCP scheduled-task registry (registered via native `Register-ScheduledTask`, not `create_scheduled_task`) — so it is invisible to any dead-man-heartbeat logic that only walks `list_scheduled_tasks`. If the pull ever throws (genuine divergence or a conflicting dirty tree), the mirror would otherwise just silently stop advancing with nobody notified. Full incident history and root-cause detail: memory file `reference_command_center_mirror_deploy_gap.md` in `~/.claude/projects/C--Users-Owner-OneDrive---Oxford-Capital-Partners/memory/` — read it if anything below is ambiguous.

KNOWN LIMITATION (do not silently paper over this in the Notion row): this CC/MCP scheduled task only fires while Claude Desktop is open — it is a business-hours-ish sampling check layered on top of the native task, NOT a 24/7 replacement for it. If Desktop was closed all day, this check simply didn't run that day; that is expected behavior of this fleet, not a defect to report.

STEPS:

1. `cd C:\Users\Owner\oxford-command-center` then `git fetch origin --quiet` (READ-ONLY — do not pull, merge, stash, or otherwise modify the tree).
2. Drift count: `git rev-list --count HEAD..origin/main`.
3. Working-tree state: `git status --short`. Known-benign baseline (do NOT flag these alone): modified `.claude/launch.json.example`, modified `package.json`, untracked `.wrangler/`, untracked `scripts/dev-watchdog.cjs`. Flag anything else unexpected, and specifically flag any REBASE/MERGE-in-progress marker (`.git/MERGE_HEAD` or similar) — that indicates a stuck `git pull --ff-only` failure from deploy-mirror.ps1.
4. Native task health: `Get-ScheduledTaskInfo -TaskName "ORA Command Center - Mirror Deploy"` — read `LastRunTime`, `LastTaskResult`, `NextRunTime`.
5. Classify:
   - HEALTHY: `LastTaskResult == 0` AND `LastRunTime` within the last ~3 hours (task fires hourly; allow scheduler jitter). A nonzero drift count BY ITSELF is NOT an alarm — it just means new commits landed on origin since the last successful hourly pull+bake and will resolve on the next hourly fire (the script pulls to HEAD every run).
   - ALARM if ANY of: `LastTaskResult != 0` (non-success exit — the pull/build/deploy threw) · `LastRunTime` older than ~3 hours during 07:00–20:00 ET (the task should have fired since) · working tree shows an unexpected change beyond the known-benign baseline in step 3, or a stuck-merge marker.
   - If `Get-ScheduledTaskInfo` or the git commands themselves error out (repo moved, task renamed/deleted, etc.) — treat that as an ALARM too ("can't verify" is not "confirmed healthy"). Never fabricate a HEALTHY verdict from incomplete data.
6. Post a completion row to the Notion Ops Hub (database ID `32b6ecd8...`) every run, every day, containing: timestamp, drift count, LastTaskResult, LastRunTime, verdict (HEALTHY/ALARM). On HEALTHY, that Notion row is the ONLY output — stay silent otherwise, no email.
7. On ALARM: send exactly ONE email via `C:\Users\Owner\.claude\scheduled-tasks\_shared\send-via-outlook.ps1`, TO `ggoldberg@oxfordra.net` ONLY (no cc — this is not the ora-am-brief Daily Brief exception), containing the diagnostic detail from steps 2-5 and a concrete next step ("check `git status` / `git log HEAD..origin/main --oneline` on `C:\Users\Owner\oxford-command-center`; if diverged or dirty, resolve manually — never auto-force-pull or discard local changes without Gabriel's OK; see `reference_command_center_mirror_deploy_gap.md` for the last incident's resolution steps"). On a non-zero exit from the send script: retry once, then ALSO flag loudly in the Notion completion row regardless — do not let the alarm silently vanish just because the email itself failed to send.
8. This task does not duplicate `ora-doctrine-integrity-guard` (governor/doctrine drift across the whole repo) or `ora-health-guard` (general connector/integrity self-heal) — it is scoped narrowly to this one deploy pipeline's freshness and does not need to touch either of those.

If any step's outcome is genuinely ambiguous (e.g., the native task was renamed, the repo path changed, Notion Ops Hub write fails), do not guess — write a QUESTIONS FOR GABRIEL note in the Notion completion row describing exactly what could not be verified, and still send the alarm email if the underlying mirror-freshness question itself remains unresolved.
